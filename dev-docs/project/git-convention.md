# Git 작업 규약 (커밋 · PR)

커밋 메시지와 PR 작성 규약. 사람과 에이전트 모두 따른다.

---

## 커밋 메시지

`<type>(<scope>): <요약>` 형식(Conventional Commits). 본문은 한국어, 무엇을·왜를 불릿으로.

### 타입 — **겉으로 드러나는 동작 변화**를 기준으로 고른다

| type | 언제 |
|---|---|
| `feat` | 새 기능·동작. **사용자가 보는 결과/동작이 달라지면** feat. |
| `fix` | 버그 수정. |
| `refactor` | **외부 동작·결과는 그대로**, 내부 구조만 변경(이동·이름 변경·중복 제거·정리). |
| `docs` | 문서만. |
| `chore` | 빌드·설정·에셋 등 코드 외. |
| `test` | 테스트 추가·수정. |
| `style` | 포맷팅 등 동작 무관 표면 변경. |

### ⚠ `refactor` 오용 주의 (이 저장소에서 실제로 틀렸던 것)

**refactor는 "결과는 똑같은데 내용(구조)만 바꾼 것"에만 쓴다.** "재구성"이라는 말에 끌려 아무 데나 붙이지 않는다.

- 데이터 모델·직렬화(필드) 형식·동작·API가 바뀌면 → refactor가 아니라 **`feat`**(또는 대규모면 rewrite). 예: 상속 기반을 모듈 조합 모델로 갈아엎으면 결과가 달라지므로 `feat`.
- **순수 재배치(refactor)와 기능 변경(feat)을 한 커밋에 섞지 않는다.** 예: "에디터 폴더 재배치(refactor)"와 "드로어 UX 개선(feat)"은 별도 커밋으로 분리한다.

붙이기 전 자문: **"겉으로 보이는 동작이 그대로인가?"** — 그렇다 → refactor / 아니다 → feat.

### 규칙

- **논리 단위로 나눈다.** 관심사가 다르면 커밋을 쪼갠다.
- 커밋·push는 **유저가 요청할 때만** 한다.
- 기본 브랜치(`main`)에서 직접 커밋하지 않는다 — 브랜치를 먼저 만든다.
- 훅 우회·서명 생략(`--no-verify` 등) 금지(유저가 명시 요청할 때만).
- 커밋 메시지 끝에 서명:
  ```
  Co-Authored-By: Claude Opus 4.8 <noreply@anthropic.com>
  ```

## PR

- 본문은 변경 요약·의도(무엇을 왜). 리뷰어가 맥락을 바로 잡게 쓴다.
- GitHub 작업은 `gh` CLI 사용.
- PR 본문 끝에:
  ```
  🤖 Generated with [Claude Code](https://claude.com/claude-code)
  ```
