# Git 작업 규약 (커밋 · PR)

커밋 메시지와 PR 작성 규약. 사람과 에이전트 모두 따른다.

---

## 커밋 메시지

`<type>(<scope>): <요약>` 형식(Conventional Commits). 본문은 한국어, 무엇을·왜를 불릿으로.

### 타입 — 겉으로 드러나는 동작 변화를 기준으로 고른다

| type | 언제 |
|---|---|
| `feat` | 새 기능·동작. 사용자가 보는 결과/동작이 달라지면 feat. |
| `fix` | 버그 수정. |
| `refactor` | 외부 동작·결과는 그대로, 내부 구조만 변경(이동·이름 변경·중복 제거·정리). |
| `docs` | 문서만. |
| `chore` | 빌드·설정·에셋 등 코드 외. |
| `test` | 테스트 추가·수정. |
| `style` | 포맷팅 등 동작 무관 표면 변경. |

`refactor`는 결과가 같고 구조만 바꾼 것에만 쓴다. 데이터 모델·직렬화 형식·동작·API가 바뀌면 `feat`다. 순수 재배치(refactor)와 기능 변경(feat)을 한 커밋에 섞지 않는다. 자문: **"겉으로 보이는 동작이 그대로인가?"** — 그렇다 → refactor / 아니다 → feat.

### 규칙

- 논리 단위로 나눈다. 관심사가 다르면 커밋을 쪼갠다.
- 커밋·push는 유저가 요청할 때만 한다.
- 기본 브랜치(`main`)에서 직접 커밋하지 않는다 — 브랜치를 먼저 만든다.
- 훅 우회·서명 생략(`--no-verify` 등)은 유저가 명시 요청할 때만.

### 스테이징 — 예상 밖 파일을 먼저 배제한다

- `git add -A`·`git commit -a`는 무관한 working 변경(특히 유저 WIP)을 삼킬 수 있다 — 스테이징 직후 `git status`로 대조하고, 의심스러우면 경로를 명시해 add한다.
- 잘못 담았으면 push 전 `reset`/`restore --staged`로 뺀다.

## PR

- 본문은 무엇을·왜·어떻게 확인했는지·위험. 리뷰어가 맥락을 바로 잡게 쓴다.
  - 확인: CI가 없으니 컴파일 확인·셀프체크·PlayMode 결과(통과 수)를 적고, 실행 안 한 것은 안 했다고 적는다.
  - 위험: 직렬화 필드·에셋 형식 변경, 에셋 직접 수정, 기존 동작 변경.
- GitHub 작업은 `gh` CLI 사용.

### 병합

- **병합은 유저가 병합을 명시할 때만 한다.** PR 생성·push 지시는 병합 지시가 아니다. "PR 확인해서 해"처럼 확인인지 병합인지 갈리는 말이면 한 줄로 되묻는다.
- **병합 전 확인** — 아래를 보고 결과를 유저에게 알린 뒤 병합한다. 하나라도 걸리면 병합하지 않고 보고한다.
  - 병합 가능(충돌 없음): `gh pr view <번호> --json mergeable,mergeStateStatus`
  - CI 체크·리뷰·코멘트: `gh pr checks <번호>`, 리뷰·코멘트 수. 지금 저장소엔 CI가 없다.
  - base 브랜치 대상이 맞는지(`main` ← 작업 브랜치).
- **병합 뒤 원격 작업 브랜치는 지운다** — PR #1~#6 브랜치가 그렇게 정리돼 있다. 브랜치 삭제는 되돌리기 어려우니 에이전트는 병합 보고 때 "브랜치 지울까요?"로 확인받고 지운다. 저장소 설정의 자동 삭제를 켤지는 유저 판단(지금 꺼짐).
- **병합 뒤 로컬 갱신** — `git fetch` → `git merge --ff-only origin/main`. 로컬에 미커밋 변경이 있으면 갱신 전에 유저에게 알리고, 이름 붙인 stash로 감쌌다 다시 적용한 뒤 파일 목록·내용·스테이징을 갱신 전과 대조한다. stash는 유저 확인 전엔 지우지 않는다.

### 일반 원칙

- **PR은 작고 한 주제로.** 큰 기능은 나눠 여러 PR로. (PR #7은 183파일로 컸다.)
- **병합 전 base를 최신으로.** 작업 브랜치가 오래 갈수록 `main`을 자주 반영해 충돌을 미리 푼다.
