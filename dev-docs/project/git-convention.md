# Git 작업 규약 (커밋 · PR)

커밋 메시지와 PR 작성 규약. 사람과 에이전트 모두 따른다.

---

## 커밋 메시지

`<type>(<scope>): <요약>` 형식(Conventional Commits). 본문은 한국어, 무엇을·왜를 불릿으로.

### 타입 — 겉으로 드러나는 동작 변화를 기준으로 고른다

| type | 언제 |
|---|---|
| `feat` | 새 기능·동작. 사용자가 보는 결과/동작이 달라지면 feat. |
| `fix` | 버그 수정. |
| `refactor` | 외부 동작·결과는 그대로, 내부 구조만 변경(이동·이름 변경·중복 제거·정리). |
| `docs` | 문서만. |
| `chore` | 빌드·설정·에셋 등 코드 외. |
| `test` | 테스트 추가·수정. |
| `style` | 포맷팅 등 동작 무관 표면 변경. |

`refactor`는 결과가 같고 구조만 바꾼 것에만 쓴다. 데이터 모델·직렬화 형식·동작·API가 바뀌면 `feat`다. 순수 재배치(refactor)와 기능 변경(feat)을 한 커밋에 섞지 않는다. 자문: **"겉으로 보이는 동작이 그대로인가?"** — 그렇다 → refactor / 아니다 → feat.

### 규칙

- 논리 단위로 나눈다. 관심사가 다르면 커밋을 쪼갠다.
- 커밋·push는 유저가 요청할 때만 한다.
- 기본 브랜치(`main`)에서 직접 커밋하지 않는다 — 브랜치를 먼저 만든다.
- 훅 우회·서명 생략(`--no-verify` 등)은 유저가 명시 요청할 때만.

---

## PR

- 본문은 변경 요약·의도(무엇을 왜). 리뷰어가 맥락을 바로 잡게 쓴다.
- GitHub 작업은 `gh` CLI 사용.
