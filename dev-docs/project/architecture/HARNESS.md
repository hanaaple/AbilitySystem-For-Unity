# HARNESS.md — architecture 문서 규약

`dev-docs/project/architecture/`(하위 폴더 포함)에 적용. 인덱스는 [overview.md](overview.md).

## 작성 규약
- **문서 상단에 `> **최종 갱신:** YYYY-MM-DD (KST)` 마커**를 둔다 — 이전 업데이트 여부(낡음) 확인용. 형식·갱신 시점·값·git fallback → docs.harness.md '날짜 작성 방법'.
- 개념·역할·시스템 간 관계를 쓴다.
- 원본(UE 등) 대비 **채택/생략·변경점**을 밝힌다 — "무엇이 다른가" 위주. 설계 이유는 사실로 짧게(정당화 수사는 아래 '서술 규율').
- 흐름·생명주기·재계산은 다이어그램/표로 남긴다.
- 채택 상태는 **구현 / 계획 / 미채택** 3단계로 범례를 구분한다 — 로드맵에 있으면 '계획', 정말 안 하는 것만 '미채택'(예: 네트워크).
- 확정된 구조·동작의 **결론**만 쓴다.
- 이름·구조·동작은 실제 코드 기준. 다이어그램의 내부 함수/타입명은 현재 코드와 일치시키고, 원본 대응은 `(UE: ...)`로 병기한다.
- 사용 예는 **실제 사용 패턴**으로 쓴다 — 실제로 안 쓰는 방식의 예시를 만들지 않는다.

## 서술 규율 — 넣지 않는 것

시스템을 **사실(구조·변경점·동작) 위주**로 쓴다. 아래는 넣지 않는다:

- **특정 게임·장르·"데모라서" 정당화** — 시스템 문서는 게임을 모른다. 범위 판단이 필요하면 "로컬 전용" 같은 **기술 조건**으로만 쓴다(장르·데모명 금지).
- **포트폴리오·평가 관점 서술** — "~를 보이는 게 목적", "판단할 수 있음을 보인다" 류.
- **가치판단 수사** — "과설계", "의도된 divergence", "버릴 이유 없다", "인상적" 등. 채택/생략은 사실로만.
- **내부 문서 코드**(`→D#`·`S#`·`INV-#`) — 외부 독자가 못 알아본다. 근거는 링크로만 잇는다(코드 자체를 본문에 노출하지 않음).

## 문서 구조

- **상위:** [ability-system/overview.md](ability-system/overview.md) — 개요·인덱스. 하위 심화 문서로 진입하는 허브.
- **하위(개별 심화):** `attribute` · `gameplay-effect` · `aggregator` · `capture` · `gameplay-ability`(계획). 각 문서는 다이어그램 + 진입점 + UE↔Unity 대응을 갖춘다.
- 새 개념이 여러 문서에 흩어지면 **전용 문서로 분리**하고 소비처는 링크로 잇는다(하위 문서에 억지로 끼워넣지 않는다). 예: 캡처 → `capture.md`.

### 검토 (미착수)

- **UE 구조 미러링 분류** — UE의 모듈/타입 계층(예: `GameplayAbilities` 모듈 → `U*` 클래스 → `F*` 구조체)을 참고해 폴더·네이밍을 분류하는 방식. 억지로 서두르지 않는다. _(유저 발의 2026-09-10)_
