# 아이템 시스템 — 백지 설계 초안 (2026-07-13)

> **성격:** 논의용 초안. 확정 아님, 구현 착수 근거 아님.
> 기존 `WeaponAttackComponent` · `EquipmentComponent` · `ItemInstance/ItemRuntime` · `ItemModule`의
> **현재 구조를 전제하지 않고** 다시 세운 안이다. 기존 코드와 겹치는 부분이 생기면 그건 결론이지 출발점이 아니다.
> 결정이 필요한 지점은 전부 **[미결]** 로 표시했다 — 그 자리는 비워 둔다.

---

## 0. 백지에서 확정된 것 = 사실뿐

설계가 아니라 **주어진 조건**. 이것만 깔고 시작한다.

- **스코프:** 소울라이크 싱글플레이. 무기 = 근접(검) + 총. 콤보 · 패링 · 특수공격이 스코프 안.
  등급/네트워크/세이브는 범위 밖.
- **GAS의 실제 표면 (코드 확인):** `AbilitySystemComponent`는 **어트리뷰트 + 게임플레이 이펙트**만 제공한다.
  - `ApplyGameplayEffectToSelf(effect) → ActiveGameplayEffectHandle`, `RemoveActiveGameplayEffect(handle)`
  - `GetAttributeCurrentValue / SetBaseAttributeValue`
  - **없는 것: GameplayAbility, 태그, 큐.** → "무기 공격 = 어빌리티 부여"는 *지금은 존재하지 않는 시스템*이다.
    그 방향은 새 시스템 구축 비용을 동반한다(그 자체가 하나의 선택지 = 아래 안 C).
- **표현:** 장착 시 무기 프리팹을 캐릭터 소켓에 붙인다.
- **입력:** 플레이어 입력 → 공격 트리거 한 줄.

## 1. 무엇이 변하는가 (설계가 답해야 할 대상)

백지 설계는 "무엇이 변하느냐"에서만 나온다. 스코프상 변하는 축은 셋이다.

| 축 | 예시 | 성격 |
|---|---|---|
| **A. 주 행동 알고리즘** | 검 = 전방 오버랩 스윙 / 총 = 히트스캔 레이 | **배타적** (검이면서 총일 수 없음). 코드가 다름 |
| **B. 주 행동의 파라미터** | 사거리, 데미지 GE, 발사 간격, 탄창 크기, 콤보 타이밍 | **데이터** |
| **C. 부가 효과** | 장착 중 이속 −5, 온히트 화상, 흡혈 | **직교** (검·총 무엇에든 곱해짐), 개수 가변 |

여기에 스코프가 강제하는 넷째가 있다:

| 축 | 예시 | 성격 |
|---|---|---|
| **D. 무기별 지속 상태 + 시간** | 콤보 단계(3타)·콤보 윈도우 만료, 탄약 수·재장전 타이머, 패링 유효 프레임 | **per-instance 가변 상태 + 매 프레임 경과** |

→ **D가 이 설계의 진짜 압력점이다.** A~C만 있으면 어떤 구조든 굴러간다.
D가 있으면 "공격 = 무상태 함수 한 방"이 성립하지 않는다. 누군가는 **무기별 상태를 들고 tick 되어야** 한다.
**[미결 D-1]** 콤보/재장전/패링을 이번 슬라이스에서 실제로 만들 것인가, 아니면 "언젠가"인가?
→ *"언젠가"라면 D는 설계 압력이 아니고, 아래 비교의 결론이 뒤집힌다.* 이건 기획 결정이라 유저 몫.

## 2. 구조 후보 (백지 3안)

### 안 A — 무기 종류 = 코드 타입 (Runtime 서브클래스)

```
ItemAsset (SO, 무상태 템플릿)
  └ WeaponAsset : ItemAsset        // Runtime 타입 지정 + 파라미터(축 B)
       SwordAsset  { range, damageGE, comboSteps[] }
       GunAsset    { range, damageGE, magazine, fireRate }

ItemInstance (POCO, per-instance 상태 소유)
  ├ WeaponRuntime (베이스: 제공 연산 = 파사드)
  │    protected OverlapForward(r) / RaycastForward(r) / ApplyEffect(target, ge)
  │    abstract Attack();  virtual Tick(dt);
  │      SwordRuntime { int _combo; float _window;  Attack() {...} }   // 축 A + D
  │      GunRuntime   { int _ammo;  float _reload;  Attack() {...} }
  └ Module[]  // 축 C — 직교 부가 효과만. OnEquip/OnUnEquip/OnHit
```

- 축 A = 서브클래스, B = SO 필드, C = 모듈 리스트, D = Runtime의 필드 + `Tick`.
- 씬 접근은 베이스가 **제공 연산(툴박스)** 으로 내어준다 → 파생은 `UnityEngine.Physics`를 직접 안 본다 (Subclass Sandbox).
- 시스템(장비/전투)은 `runtime.Attack()` 한 줄. **무기 종류 분기 없음.**
- 값: 무기 추가 = 에셋 클래스 + 런타임 클래스 2개. 콤보/탄약이 자연스럽게 자기 자리에 앉는다.
- 대가: 축 A와 B가 두 파일로 쪼개져 짝을 맞춰야 함(SwordAsset ↔ SwordRuntime). 클래스 수 증가.

### 안 B — 무기 종류 = 데이터 + 시스템이 알고리즘 보유

```
ItemAsset { modules[] }          // 모듈이 IMeleeAttack / IHitscanAttack 같은 능력 인터페이스 구현
WeaponAttackComponent (시스템)   // 판정·GE 적용을 전부 여기서. 능력 인터페이스로 분기
```

- 축 A = 시스템 안의 분기, B = 모듈 필드, C = 모듈, **D = 갈 곳이 없다.**
- 값: 클래스 최소. 물리 판정 코드가 한 군데. "물리는 시스템의 일"이라는 설명이 성립.
- 대가: **축 D가 오면 무너진다.** 콤보 카운터·탄약을 시스템이 "장착 아이템별"로 들고 있어야 하고
  (= 결국 per-instance 상태 테이블을 시스템이 재발명), 무기 종류가 늘 때마다 시스템 분기가 늘어난다.
- **D-1이 "언젠가"라면 이 안이 정답에 가깝다.** D-1이 "이번 슬라이스"라면 도입 즉시 부채가 된다.

### 안 C — 무기 종류 = 어빌리티 (GAS 확장)

```
GameplayAbility 시스템을 새로 만든다 → 무기 장착 시 ASC에 SwordComboAbility / GunFireAbility 부여
```

- 축 A/B/D 전부 어빌리티가 흡수(어빌리티는 원래 상태·쿨다운·태스크를 가짐). C = 여전히 모듈 or 이펙트.
- 값: 소울라이크의 콤보·패링·특수공격은 **원래 어빌리티 문제**다. 장기적으로 가장 정합적.
  포트폴리오에서 "GAS를 어트리뷰트·이펙트에서 어빌리티까지 확장했다"는 서사가 됨.
- 대가: **아이템 시스템 논의를 하다가 어빌리티 시스템을 새로 짓는 일이 된다.** 지금 없는 시스템이다.
  범위 폭발 위험이 가장 크고, 북극성("트리거 오기 전엔 복잡하게 만들지 않는다")과 정면 충돌 가능.
- **[미결 C-1]** 어빌리티 시스템은 이 프로젝트 로드맵에 원래 있는가? 있다면 순서가 아이템보다 앞인가 뒤인가?
  → 뒤라면 안 A/B로 가되 **나중에 안 C로 이행 가능한 형태**인지가 평가 기준이 된다.

## 3. 세 안이 공통으로 답해야 하는 나머지 (안 무관)

### 3.1 부가 효과(축 C) = 모듈
- `[SerializeReference]` + SubclassSelector로 SO에 리스트로 담는다. 개수 가변, 조합 자유.
- 훅: `OnEquip` / `OnUnEquip`(장착 중 지속 GE — 이속 −5가 여기) / `OnHit(target)`(온히트 효과).
- per-item 가변 상태(회수용 `ActiveGameplayEffectHandle` 등)는 **모듈이 아니라 인스턴스가** 보유해야 한다
  (SO는 여러 아이템이 공유하는 템플릿 → 모듈 필드에 런타임 값을 쓰면 인스턴스끼리 덮어씀).
- **[미결 M-1]** `OnHit` 훅이 성립하려면 "누가 맞았는지"를 히트 판정 주체가 모듈에 알려줘야 한다.
  안 A면 Runtime이, 안 B면 시스템이 방송. 이 방송 경로를 만들 것인지 = 온히트 효과를 이번에 다룰 것인지.

### 3.2 씬 접근 (지금 깨져 있는 지점)
현재 `ModuleContext`가 **빈 클래스**라 장착 시 모듈 lifecycle 호출이 통째로 주석 처리돼 있고,
그래서 StatModifier(이속 −5)가 죽어 있다. 어떤 안을 고르든 이건 풀어야 한다.

필요한 것은 결국 **소유자 ASC 하나**(+ 판정하려면 소유자 Transform).
- 다운캐스트 없는 **구체 컨텍스트 타입 하나**를 장착 시 주입하면 끝난다(과거 `AbilitySystemModuleContext` 다운캐스트 문제의 원인은 "베이스 컨텍스트 + 파생 캐스팅" 구조였다).
- 물리 판정까지 아이템 코드가 한다면(안 A), 컨텍스트를 날것으로 노출하기보다 **베이스가 제공 연산으로 감싸는** 쪽이 중복을 막는다.
- **[미결 X-1]** 컨텍스트가 실어야 할 최소 집합: ASC만? ASC + Transform? 그 이상(레이어 마스크·팀 판별)?
  → 팀/적대 판별을 어떻게 할지가 아직 없다. 현재는 "자기 자신이 아니면 때린다"로 임시 동작 중.

### 3.3 장비 컴포넌트
- 책임: **슬롯 상태 + 소켓 표현 + 장착/해제 시 lifecycle 구동.** 그 이상 아님.
- 공격 실행은 여기 두지 않는다(장비 도메인 ≠ 전투 도메인).
- **[미결 E-1]** 축 D가 채택되면 누군가 매 프레임 `Tick`을 돌려야 한다. 장착 아이템의 tick 주체 =
  장비 컴포넌트인가, 별도 얇은 전투 드라이버인가?

## 4. 결정 순서 (제안 — 이대로 할지도 유저 결정)

1. **D-1** (콤보/탄약/패링 = 이번인가 나중인가) — 이게 A vs B를 사실상 가른다.
2. **C-1** (어빌리티 시스템이 로드맵에 있는가) — 있으면 A/B는 "이행 가능한가"로 기준이 바뀐다.
3. 그다음에야 A/B/C 중 택1 → 그 뒤 X-1(컨텍스트) · M-1(온히트) · E-1(tick 주체).

**지금 코드는 손대지 않는다.** 위 미결이 서기 전까지 이 문서는 논의용일 뿐이다.
