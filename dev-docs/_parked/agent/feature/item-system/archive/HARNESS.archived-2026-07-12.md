# HARNESS.md — 아이템 시스템 구현 하네스

> 이 문서는 AI 에이전트가 본 프로젝트에서 구현 작업을 수행할 때의 **방향성·제약·운영 규약**이다.
> 구현의 자세한 방법은 여기서 정하지 않는다. **무엇을 지키는가, 무엇을 넘지 않는가, 어떻게 검증·보고·인계하는가**만 정한다.

---

## 1. 프로젝트 방향성 (에이전트가 내면화할 것)

- **목적:** 게임 클라이언트 프로그래머 포트폴리오. 산출물의 크기가 아니라 **판단의 질과 굴러가는 데모**가 평가 대상.
- **북극성:** "필요해지는 트리거가 오기 전엔 더 복잡하게 만들지 않는다." 모든 구현 판단에서 단순한 쪽이 디폴트.
- **스코프:** 소울라이크 싱글플레이, 근접+총, 콤보·패링·특수공격. 인벤토리·개수/스택은 `inventory` feature로 **스코프 안**(2026-07-05 유저 결정 — inventory D2). 등급/네트워크/세이브는 여전히 **범위 밖** — 요청받지 않는 한 그 방향의 코드·필드·주석을 만들지 않는다.
- **완성의 정의:** "설계가 아름답다"가 아니라 **"수직 슬라이스가 실제로 굴러간다 + 왜 이렇게 했는지 문서로 설명된다"**.

## 2. 아키텍처 불변 조건 (INVARIANTS — 위반 금지)

에이전트는 어떤 요청을 수행하든 아래를 위반하는 코드를 작성하지 않는다.     위반이 불가피해 보이면 **작업을 멈추고 보고**한다.

| ID | 불변 조건 | 위반 예시 (금지) |
|---|---|---|
| INV-1 | `ItemData`(SO)는 **무상태**. 런타임 값 쓰기 금지 | SO 필드에 쿨다운 잔여시간 저장 |
| INV-2 | `ItemData` / `ItemInstance`에 **아이템별 상속 금지**. 특수화는 Module·인터페이스 조합으로. 금지 대상은 *상속*뿐 — 별개 `ItemRuntime` 클래스를 **합성**(`ItemInstance`가 멤버로 보유)으로 두는 건 상속이 아니므로 허용된다(INV-10) | `FireSwordInstance : ItemInstance` (상속). ↔ 허용: `ItemInstance`가 `FireSwordRuntime`을 멤버로 보유(합성) |
| INV-3 | Module은 씬·UI·GameObject를 **직접 만지지 않는다**. 결정만 하고 표현은 요청으로 넘긴다 | Module 안에서 `Instantiate(vfxPrefab)` |
| INV-4 | `ItemBehaviour`(MonoBehaviour)에 **동작 로직 금지**. 표현·이벤트 중계만 | Behaviour에서 데미지 계산 |
| INV-5 | per-item 상태는 `ItemInstance` 소유(`IModuleState[]` 병렬 배열). 캐스트는 제네릭 베이스 한 곳에만 | 작성자 코드에서 `(BleedState)state` 캐스팅 |
| INV-6 | 공유 상태(콤보·스태미나·타깃)는 **캐릭터(CombatActor) 소유**. 무기 소유 금지 | 무기 Instance에 콤보 카운트 |
| INV-7 | 계층 흐름은 **단방향**: Module → Instance → 소유자 → Behaviour/UI. 역방향 참조 금지 | Module이 UI 매니저 참조 |
| INV-8 | UI·Behaviour는 **이벤트 구독**으로 갱신. 매 프레임 폴링 금지 | Update에서 Instance 상태 조회해 UI 갱신 |
| INV-9 | `Dictionary<string, object>` 형태의 untyped 저장 금지. 공유·상태 모두 타입드 유지 | 문자열 키 블랙보드 |
| INV-10 | **재사용 판별식**: 여러 아이템에 붙을 수 있으면 Module, 한 아이템 전용이면 전용 Runtime(`ItemRuntime`). 전용 Runtime은 Module로 분해하면 의미가 왜곡되는(다른 아이템에 붙는 게 부자연스러운) **아이템 전체 스코프의 자유형 로직·구조**에 쓴다. 반드시 **합성**(`ItemInstance`가 멤버 보유, 상속 아님 — INV-2)이고 **per-instance 생성**(SO 무상태 — INV-1). Module이 항상 기본, Runtime은 예외이며 채택 시 "왜 Module로 안 되는지" 한 줄 근거. 누적 3개 초과 시 중단·보고 | 유니크 로직을 억지로 Module 여러 개로 분해 |
| INV-11 | 시스템의 필수 요구는 특정 Module이 아니라 **인터페이스 능력**으로 선언·검증 | `if (module is MeleeAttackModule)` 하드코딩 |
| INV-12 | C# 언어 기능은 **C# 9 이하** (Unity 6). record는 직렬화 타입에 사용 금지 | 직렬화 클래스에 record |

## 3. 작업 규약 (AI Agent Protocol)

### 3-1. 작업 시작 전
- 요청을 **수직 슬라이스 단위**로 해석한다: 완료 시점에 에디터에서 실행해 눈으로 확인 가능한 상태가 목표.
- 요청이 §1 스코프 밖 기능을 암시하면, 구현 전에 **스코프 확인 질문 1회**. 답이 없으면 스코프 내로 좁혀 진행하고 그 사실을 명시.
- 기존 코드를 수정할 때는 수정 대상 파일을 먼저 읽고, 불변 조건과의 충돌 여부를 확인한 뒤 작업한다.

### 3-2. 구현 중 판단 규칙
- **애매하면 단순한 쪽**: 추상화 추가 vs 직접 구현 사이에서 망설여지면 직접 구현. 추상화는 두 번째 사용처가 나타났을 때.
- **새 인터페이스/베이스 클래스 추가는 보고 대상**: 만들기 전에 "왜 기존 축으로 안 되는지" 한 줄 근거를 남긴다.
- **파일 배치**: 기존 폴더 구조(Data / Strategies / Abilities(Modules) / Runtime / Interfaces)를 따르고, 새 폴더 신설은 보고 후.
- **네이밍**: Module은 `~Module` 또는 행동명(`IgniteOnHit`), 상태는 `~State`, 능력 인터페이스는 `I~Provider`/`I~Contributor` 계열 유지.
- 주석은 "무엇"이 아니라 **"왜"** — 특히 불변 조건과 관련된 결정 지점에는 해당 INV-ID를 주석으로 남긴다. (예: `// INV-5: 캐스트는 여기 한 곳`)

### 3-3. 금지 행동
- 요청받지 않은 리팩터링·스타일 변경·기능 확장 금지. 발견한 개선점은 구현하지 말고 §5 보고에 적는다.
- 테스트·검증을 통과시키기 위한 우회(검증 로직 약화, 어설션 삭제, 예외 삼키기) 금지.
- 불변 조건을 "임시로" 어기는 TODO 코드 금지. 어겨야만 한다면 멈추고 보고.
- 설계 문서(ADR·Summary)를 임의 수정 금지. 설계 변경이 필요하면 제안만 하고 사람 승인 후 반영.

## 4. 검증 (Verification)

각 슬라이스는 아래 3단 검증을 통과해야 "완료"를 선언할 수 있다.

### V1 — 정적 검증 (매 작업)
- 컴파일 에러/경고 0. Unity 콘솔 기준.
- 불변 조건 자가 점검: 이번 변경분에 대해 §2 표를 훑고, 각 INV에 대해 "해당 없음 / 준수" 중 하나로 체크한 결과를 보고에 포함.

### V2 — 기능 검증 (슬라이스 완료 시)
- **에디터 실행 가능한 재현 절차**를 함께 제공한다: "씬 X 열기 → Play → 키 입력 → 기대 결과". 사람이 30초 안에 따라할 수 있어야 함.
- 가능한 것은 EditMode 테스트로: 특히 `ItemInstance`·Module은 POCO/SO라 씬 없이 테스트 가능하도록 설계되어 있다 — **씬 없이 테스트가 안 짜지면 그 자체가 INV-3/4 위반 신호**이므로 보고.
- 데이터 검증: 새 `ItemData` 에셋은 필수 능력(인터페이스) 검증(`OnValidate`)을 통과해야 함.

### V3 — 회귀 확인 (기존 기능 접점이 있을 때)
- 변경이 닿은 기존 슬라이스의 재현 절차를 재실행해 깨짐 여부 확인. 깨졌다면 고치기 전에 **원인을 먼저 보고** (조용히 고치고 넘어가지 않는다).

## 5. 실시간 피드백 (작업 중 보고 프로토콜)

에이전트는 다음 시점에 **즉시, 짧게** 보고한다. 보고 없이 진행하지 않는다.

| 시점 | 보고 형식 |
|---|---|
| 불변 조건과 충돌 발견 | `[INV 충돌] INV-N: 상황 / 가능한 선택지 2개 / 권장안` → **대기** |
| 스코프 밖 요구 감지 | `[스코프] 요청이 X를 암시함. 범위 내 대안: Y` → 1회 질문 |
| 설계 문서와 요청 불일치 | `[설계 충돌] 문서 결정 N vs 요청. 어느 쪽 우선?` → **대기** |
| 새 추상화(인터페이스/베이스) 필요 판단 | `[추상화 제안] 이유 1줄 + 대안(직접구현) 비교` → 진행하되 명시 |
| 예상 밖 부수효과·회귀 발견 | `[회귀] 무엇이 왜 깨졌는지` → 수정 전 보고 |
| 개선점 발견 (요청 외) | 구현하지 않고 `[제안]`으로 목록화만 |

원칙: **막히면 오래 헤매지 말고 선택지를 들고 온다.** "30분 이상 같은 문제를 도는 중"이면 그 자체가 보고 사유.

## 6. 정리 및 인계 (Handoff)

세션/작업이 끝날 때 인계는 **별도 Handoff 파일 없이** 아래 세 곳에 반영한다. 목적은 다음 세션의 에이전트/사람이 컨텍스트 없이 이어받는 것.

- **`worklog.md`** — 무엇을 왜 했나(막힌 점·해결 포함) + 검증 상태(V1/V2/V3).
- **progress `## 다음 작업`** — 다음 사람이 첫 30분에 할 일 + 미해결·제안.
- **`decisions.md`** — 내린 판단과 근거 (품질 기준: 일반 HARNESS §8; 특히 INV·재사용 판별식).

**판단이 문서화 안 된 코드는 인계로 인정하지 않는다** — 코드와 "왜"가 세트다 (포트폴리오 목적상 판단 기록 자체가 산출물).

| S6 | 콤보 무브셋 | 3타 콤보가 애니·타이밍대로 진행 | ☐ |
| S7 | 기여 배선 (IStatContributor + WireModules) | 장착 시 버프가 캐릭터 스탯에 반영, 해제 시 회수 | ☐ |
| S8 | 특수공격 + 패링/가드 | 스킬 입력·패링 윈도우 동작 | ☐ |
| S9 | 두 번째 온히트 효과 (감전 체이닝) | **코드 0줄, 에셋 추가만으로** 신규 효과 동작 | ☐ |
| S10 | 저작 툴링 (커스텀 인스펙터 요약) | 무기 에셋 하나에서 조합이 한 화면에 보인다 | ☐ |

- 상태 표기는 이 파일에서 직접 갱신(☐ → ☑ + 날짜). 이 표가 **진행의 단일 진실**이다.
- S9는 설계 전체의 검증 슬라이스다: 이게 "코드 0줄"로 안 되면 설계가 약속을 어긴 것이므로 원인을 ADR에 기록한다.

## 부록 — 빠른 판별 치트시트 (에이전트 상시 참조)

- 이 로직, 다른 아이템에도 붙나? → **예: Module / 아니오: 통짜 Module or 전용 Runtime**
- 이 상태, 누가 오래 갖고 있어야 하나? → **아이템 수명: ItemInstance / 캐릭터 수명: CombatActor / 이번 호출뿐: Context 파라미터**
- 이 코드, 씬·UI를 아나? → **안다면 Module·Instance에 못 들어감 (Behaviour/시스템으로)**
- 새 추상화가 필요해 보이나? → **두 번째 사용처가 있나? 없으면 직접 구현**
- 시스템이 뭔가를 "필수"로 요구하나? → **구체 클래스가 아니라 인터페이스 능력으로**
