# Git 규약 (커밋 · PR)

## 커밋 메시지

`<type>(<scope>): <요약>` 형식(Conventional Commits)을 쓴다. 본문은 한국어로, 무엇을 왜 바꿨는지 불릿으로 적는다.

### 타입

겉으로 드러나는 동작이 바뀌었는지를 기준으로 고른다.

| type | 언제 |
|---|---|
| `feat` | 새 기능·동작. 사용자가 보는 결과나 동작이 달라진다. |
| `fix` | 버그 수정 |
| `refactor` | 외부 동작·결과는 그대로이고 내부 구조만 바뀐다(이동·이름 변경·중복 제거·정리). |
| `docs` | 문서만 |
| `chore` | 빌드·설정·에셋 등 코드 외 |
| `test` | 테스트 추가·수정 |
| `style` | 포맷 등 동작과 무관한 표면 변경 |

데이터 모델·직렬화 형식·동작·API가 바뀌면 `refactor`가 아니라 `feat`다. 순수 재배치와 기능 변경은 한 커밋에 섞지 않는다.

### 규칙

- 논리 단위로 나눈다. 관심사가 다르면 커밋을 쪼갠다.
- 기본 브랜치(`main`)에 직접 커밋하지 않는다. 작업 브랜치를 먼저 만든다.
- `git add -A`·`git commit -a`는 관계없는 작업 중 변경까지 담을 수 있다. 스테이징 뒤 `git status`로 확인하고, 애매하면 경로를 지정해 add 한다.

## PR

- 본문에는 무엇을, 왜, 어떻게 확인했는지, 위험 요소를 쓴다.
  - 확인: CI가 없으므로 컴파일 확인, 셀프체크·PlayMode 테스트 결과(통과 수)를 적는다. 실행하지 않은 것은 안 했다고 적는다.
  - 위험: 직렬화 필드·에셋 형식 변경, 에셋 직접 수정, 기존 동작 변경
- PR은 작게, 한 주제로 만든다. 큰 기능은 여러 PR로 나눈다.
- 작업 브랜치가 오래가면 `main`을 자주 반영해 충돌을 미리 푼다.

### 병합

- 병합 전에 확인한다.
  - 충돌 없음: `gh pr view <번호> --json mergeable,mergeStateStatus`
  - 리뷰·코멘트 (CI는 아직 없다)
  - base가 `main`인지
- 병합한 뒤 원격 작업 브랜치는 지운다.
- 로컬은 `git fetch` → `git merge --ff-only origin/main`으로 갱신한다.
