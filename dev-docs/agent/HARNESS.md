# HARNESS.md — Agent 작업 규약

> 이 문서는 **feature 현황 추적과 세션 작업 프로토콜**을 정의한다. 진입점은 루트의 `CLAUDE.md`이며, 실제 구현 작업(feature 착수·진행·완료)에 들어가기 전 이 문서를 읽는다.
> 에이전트 작업 문서는 전부 `dev-docs/agent/`에 있다.

---

## 1. 핵심 원칙

1. **문서가 곧 상태(State)다.** Agent의 컨텍스트는 세션마다 초기화된다. 세션 간 유일한 기억은 `dev-docs/` 문서이므로, 문서에 기록되지 않은 작업은 없었던 작업으로 간주한다.
2. **읽기 → 작업 → 기록.** 모든 세션은 이 3단계를 따른다. 기록 없이 세션을 종료하지 않는다.
3. **하나의 세션, 하나의 feature.** 한 세션에서는 원칙적으로 하나의 feature에만 집중한다. 다른 feature의 코드를 수정해야 한다면 해당 feature의 progress에 사유를 기록한다.
4. **추측 금지.** progress 문서와 실제 코드가 불일치하면, 코드를 진실로 보고 progress 문서를 수정한 뒤 작업을 시작한다.

---

## 2. 디렉토리 구조

```
dev-docs/
├── agent/                      # 에이전트 작업용 (본 규약이 관리하는 대상)
│   ├── HARNESS.md              # 본 문서 (프로세스 규약: feature 추적·세션 프로토콜)
│   ├── feature-list.md         # 전체 feature 목록 및 상태 대시보드
│   ├── TODO-BOARD.md           # 잡다한 작업·개인 TODO·이슈 보드 (feature-list와 별개 레이어; §7)
│   ├── feature-progress-TEMPLATE.md
│   └── feature/
│       ├── <feature-id>/           # 단일 feature (그룹 불필요 시)
│       │   ├── progress.md          # 진행 문서 (필수)
│       │   ├── worklog.md           # 작업 로그 (아카이브; progress에서 분리 — §5)
│       │   ├── decisions.md         # 결정 기록 상세 (progress엔 요지 인덱스 — §5·§8)
│       │   └── HARNESS.md           # feature 전용 하네스/설계·기획 문서 (선택)
│       └── <group-id>/             # feature 그룹 (대분류; 하위 feature가 많을 때 묶는다)
│           ├── HARNESS.md           # 그룹 공유 하네스/설계 (선택, 하위 전체를 지배)
│           └── <feature-id>/        # 하위 feature
│               ├── progress.md      # 진행 문서 (필수)
│               ├── worklog.md       # 작업 로그 (아카이브; §5)
│               └── decisions.md     # 결정 기록 상세 (§5·§8)
└── project/                    # 프로젝트 자료 (작업 규약 대상 아님)
    ├── design.md               # 게임 기획
    ├── CODE_CONVENTION.md      # 코드 컨벤션
    ├── dev-tools.md            # 개발 도구 설정
    └── architecture/           # 시스템 구조·설계 문서
```

- feature-id·group-id는 **kebab-case 영문 소문자**로 짓는다. (예: `combat-core`, `enemy-ai`, `item-system`)
- 각 feature는 폴더를 가지며 진행 문서는 반드시 그 안에 `progress.md`로 둔다. 단일 feature는 `feature/<feature-id>/`, 그룹 하위 feature는 `feature/<group-id>/<feature-id>/`.
- **그룹(대분류):** 한 도메인의 하위 feature가 여러 개로 늘어 대시보드 가독성이 떨어지면 `feature/<group-id>/`로 묶는다. (예: `item-system` → `item`·`inventory`·`equipment`, `ability-system` → `gameplay-effect`·`attribute`) 그룹 자체는 progress를 갖지 않으며, 하위 feature 전체를 지배하는 **공유 불변조건·설계**가 있으면 그룹 폴더에 `HARNESS.md`를 둔다(하위 feature는 이를 참조하고 중복 정의하지 않는다).
- feature 고유의 **구현 방향·불변 조건·로드맵 또는 설계/기획**이 방대하면 같은 폴더에 `HARNESS.md`(feature 전용 하네스/설계 문서)를 둔다. 본 문서(일반 HARNESS)는 **프로세스 규약**, feature/그룹 `HARNESS.md`는 **그 feature의 구현 규약/설계**로 역할이 다르다. 충돌 시 일반 HARNESS의 프로세스 규약이 우선하되 충돌을 보고한다.
- `feature-list.md`에 없는 feature의 폴더를 만들지 않는다. (등록이 먼저다)

## 3. 세션 프로토콜 (Agent 필수 절차)

### 3.1 세션 시작 시 (이어하기)

**단일 재개 지점은 `NOW.md`다.** 유저가 "하던거 하자"류로 이어하기를 요청하면 — 또는 세션을 그냥 이어가면 — **`NOW.md` 하나만 읽고 곧장 `## ▶ 지금 할 일`부터 실행한다.** 이게 목적이자 규칙이다: **전부 확인하지 말고 명확·빠르게 재개한다.**

- feature-list·progress·worklog·코드·TODO-BOARD를 **미리 훑지 않는다.** NOW.md가 지목한 액션을 바로 하고, 막히거나 더 깊은 맥락이 필요할 때만 NOW.md에 걸린 링크(해당 feature progress 등)를 연다.
- IN-PROGRESS feature가 여럿이어도 **어느 걸 이어할지 고민하지 않는다** — NOW.md가 지목한 하나가 진실이다.
- NOW.md의 선행조건(예: Unity MCP)이 안 갖춰졌으면, NOW.md에 적힌 대안/요청을 그대로 따른다(예: "에디터 열고 세션 재시작" 1줄 요청 후 대기).
- 유저 지시가 NOW.md와 다르면 **유저 지시가 우선**. 그 지시가 새 초점이면 NOW.md를 그 자리에서 갱신하고 진행한다.

> feature-list(현황 대시보드)·TODO-BOARD(잡다한 backlog)·progress(feature 상세)는 각자 역할이 있지만 **재개 메커니즘이 아니다.** 재개는 오직 NOW.md.

### 3.2 작업 중

- 설계 결정(트레이드오프가 있는 선택)을 내리면 즉시 feature 폴더 `decisions.md`에 상세 기록 + progress `## 결정 기록`에 요지 한 줄. **품질 기준은 §8** (포트폴리오·면접 산출물이므로 상세히).
- 작업이 막히면(외부 의존성, 미확정 스펙 등) `## 블로커`에 기록하고 사용자에게 보고한다.
- feature 범위가 커지면 임의로 확장하지 않고, 분리 제안을 사용자에게 보고한다.
- 컨텍스트가 길어지면 세션 종료 전이라도 `worklog.md`·progress `## 다음 작업`에 중간 요약을 남긴다. (컨텍스트 압축·리셋으로 진행 내용이 유실되지 않게)
- 문서(특히 하네스·decisions·worklog)에 **유저 의도를 넘어선 각색·해석·함의**를 남기려 하면 — 금지가 아니라 — **쓰기 전에 무조건 유저에게 먼저 묻는다.** 물어서 승인되면 남겨도 된다. 기록의 기준은 유저의 의도다.
- **토큰(컨텍스트)이 크게 나갈 작업은 착수 전에 규모·방식을 먼저 묻는다.** 도구 호출·조회가 여러 번 반복될 게 예상되는 작업 — 광범위 참조 추적, 정합성 검증(주석/코드 구분·using 파급 등), 다수 파일 일괄 편집, 대규모 리팩터 — 은 바로 시작하지 말고 예상 비용을 알리고 **범위 축소·검증 위임 옵션**을 제시한 뒤 진행한다. (예: "범위를 X만으로 좁힐까", "컴파일 검증은 유저가 Unity에서 볼까".)
  - *사례(2026-07-08):* 에디터 스크립트 feature-local `Editor/` 통일 + `EquipmentComponent`·`IEquippable`·`SlotType`을 `Core.ItemSystem.Equipment`로 승격. namespace 12+파일 변경 자체는 작았으나, **컴파일을 유저가 하는 구조라 참조 정합성을 코드로 직접 검증**(참조처 grep을 주석/코드까지 구분, 파일별 using 파급 추적, 이동 후 잔재 검증)하느라 조회가 크게 나갔다. 착수 전 "이만한 검증 비용이 든다 — 범위를 좁힐지, 컴파일은 Unity에서 확인할지"를 먼저 물었어야 한다.
- **좁은 스코프·가정 위에서만 성립하는 구현은, 그 한정성을 스스로 표면화해 착수 전에 확인한다.** 설계 제약·스코프·정책이 여러 갈래로 갈리면 — 특히 "어디까지를 한 단위/스코프로 볼지", 되돌리기 비용 있는 데이터·구조 선택, 동작 정책(우선순위·중복 처리·기본값 등) — 한 쪽을 임의로 정하지 말고 유저에게 제시해 확정받는다. **갈림이 겉으로 드러나지 않아도**, 내가 특정 좁은 상황에서만 동작하도록 구현하려 하면 그 가정을 먼저 밝혀 확인한다(유저가 나중에 "그럼 X는?" 하고 지적하기 전에 스스로). 이미 짜기 시작했어도 한정성이 보이면 멈추고 묻는다.
  - *사례(2026-07-08):* `SubclassSelector`의 중복 제외(`uniqueInList`)를 **"자기가 속한 리스트만 스캔"** 이라는 좁은 스코프로 조용히 구현했다. 유저가 "리스트 외부는?"이라 물어서야 그 한정성이 드러났다 — 유일성 스코프(자기 리스트 / 같은 오브젝트 전체 / 커스텀 태그 그룹 / 프로젝트 전역)는 수집 방식·비용·규약이 전혀 달라 처음부터 "이 구현은 리스트 내부 한정인데 그 범위면 되냐"를 밝히고 물었어야 했다.

### 3.3 세션 종료 시 (필수)

1. **`NOW.md`를 다음 재개 지점으로 갱신한다 (최우선).** 이번 세션 종료 시점 기준으로 `## ▶ 지금 할 일`(feature + 다음 액션)과 `## ⚙ 선행조건`을 다시 쓴다. — **다음 세션이 NOW.md만 읽고 즉시 재개할 수 있어야 한다.** 액션이 외부 선행조건(Unity MCP 켜짐·에디터 열림·세션 재시작·특정 에셋 등)을 요구하면 반드시 여기 명시(다음 세션이 재발견하지 않게).
2. feature 폴더의 `worklog.md`에 오늘 날짜로 수행한 작업을 요약 기록한다. (로그는 아카이브라 progress.md에서 분리 — §5)
3. 해당 feature progress의 `## 다음 작업`을 갱신한다. (NOW.md는 "지금 하나", progress `## 다음 작업`은 그 feature의 이후 순서 — 둘이 어긋나지 않게)
4. feature 상태가 변했으면 progress 상단의 상태와 `feature-list.md`의 상태를 **둘 다** 갱신한다. (단일 갱신 금지 — 항상 동기화)

### 3.4 최종 갱신 타임스탬프 & 하류 문서 동기화 판별

**목적:** feature/구현이 바뀐 **시각**을 기록해, 그를 요약·소개하는 하류 문서(`project/architecture/*`, `wiki/`)가 **무엇을 갱신해야 하는지 시각 비교로 판별**할 수 있게 한다.

- **시각 형식:** 모든 `최종 갱신`은 **`YYYY-MM-DD HH:MM` (KST, +09:00)** 로 시각까지 적는다. 문서를 실제로 바꿀 때마다 현재 시각으로 갱신한다. (progress·feature-list·TODO-BOARD·architecture·wiki 공통)
- **상류 / 하류:** 진실의 출처는 **코드 + feature `progress.md`**(상류). 이를 요약하는 `architecture/*`·`wiki/`는 **하류**다.
- **하류의 반영 기준 마커:** 하류 문서(또는 wiki 섹션)는 상단/메타에 **`반영 기준: <상류 feature-id> @ <ts>`** 를 둔다 — "이 문서는 그 상류를 이 시각 상태로 반영함"의 뜻.
- **갱신 필요 판별:** 하류의 `반영 기준 ts` < 상류 feature의 `최종 갱신 ts` 이면 그 하류는 **낡음(갱신 후보)**. "무엇을 갱신할지"는 이 비교로 좁힌다.
  - `architecture/*`는 코드 변경과 **같은 세션 동기화가 원칙**(CLAUDE.md)이라 항상 최신이어야 한다.
  - `wiki/`는 `wiki/HARNESS.md` §0에 따라 **요청 시에만** 갱신하되, 이 비교를 낡음 리마인드의 근거로 쓴다.

## 4. feature-list.md 규약

`feature-list.md`는 프로젝트의 대시보드이며, 아래 형식을 따른다.

### 4.1 상태 정의

| 상태 | 의미 |
|---|---|
| `📋 PLANNED` | 등록만 됨. 설계/구현 미착수 |
| `🔧 IN-PROGRESS` | 현재 작업 중 |
| `⏸️ BLOCKED` | 블로커로 중단됨 (progress에 사유 필수) |
| `✅ DONE` | 완료. 수용 기준 충족 확인됨 |
| `🗄️ ARCHIVED` | 폐기 또는 통합됨 (사유 필수) |

### 4.2 상태 전이 규칙

```
PLANNED → IN-PROGRESS → DONE
              ↕
           BLOCKED
(모든 상태 → ARCHIVED 가능, 사유 필수)
```

- `DONE` 처리는 progress의 `## 수용 기준`이 전부 체크된 경우에만 허용한다.
- `DONE`인 feature를 다시 수정해야 하면 `IN-PROGRESS`로 되돌리고 사유를 기록한다.

### 4.3 목록 형식

그룹이 있으면 `###` 헤더로 묶고, 그룹 공유 하네스가 있으면 헤더 아래 링크한다. 그룹이 필요 없는 단일 feature는 헤더 없이 표 행으로 둔다.

```markdown
### 🧩 <group-id> — <그룹 이름>
공유 하네스: [HARNESS](feature/<group-id>/HARNESS.md)

| ID | Feature | 상태 | 우선순위 | 의존 | Progress |
|---|---|---|---|---|---|
| combat-core | 근접 전투 코어 | 🔧 IN-PROGRESS | P0 | - | [progress](feature/<group-id>/combat-core/progress.md) |
```

- 우선순위: `P0`(필수) / `P1`(중요) / `P2`(여유 시)
- `의존` 열에는 선행되어야 하는 feature-id를 적는다.
- 하위 feature ID는 그룹 안에서만 유일하면 된다(그룹이 네임스페이스). 표기는 짧게 `item`·`inventory`처럼.

## 5. progress.md 규약

각 progress 파일은 아래 템플릿 구조를 유지한다. **섹션을 임의로 삭제하지 않는다.**

```markdown
# <feature-id> — <Feature 이름>

- 상태: 🔧 IN-PROGRESS
- 우선순위: P0
- 최종 갱신: YYYY-MM-DD HH:MM  (KST, +09:00 — §3.4)

## 목표
이 feature가 완성되면 무엇이 가능해지는가. (1~3문장)

## 수용 기준 (Definition of Done)
- [ ] 검증 가능한 조건 1
- [ ] 검증 가능한 조건 2

## 범위
### 포함
### 제외 (명시적으로 하지 않을 것)

## 설계 개요
핵심 구조, 관련 클래스/파일, 데이터 흐름 요약.

## 세부 TODO (구현 체크리스트)
이 feature를 완성하는 데 필요한 구현 작업을 순서대로 나열한다. 진행하며 ☑ 한다.
- [ ] 1. 작업 항목
- [ ] 2. 작업 항목

## 결정 기록
→ [decisions.md](decisions.md) (상세). progress엔 요지 인덱스만 (decisions.md와 같은 `D#` 공유).
| ID | 날짜 | 결정 (요지) |
|---|---|---|

## 작업 로그
→ [worklog.md](worklog.md) (시간순 이력은 별 파일). 재개 앵커는 아래 `## 다음 작업`.

## 블로커
(없으면 "없음"으로 명시)

## 다음 작업
1. 가장 먼저 할 일 (구체적으로: 파일, 클래스, 목표 단위)
2. 그 다음 할 일
```

### progress 작성 규칙

- **세부 TODO vs 수용 기준 vs 다음 작업** (혼동 금지):
  - `수용 기준` = 완료 판정(검증 가능한 **결과**). `세부 TODO` = 그 결과를 만들기 위한 **구현 작업 backlog**(과정). `다음 작업` = 세부 TODO 중 **다음 세션에 착수할 항목**을 구체 실행 지시로 지목.
  - 세부 TODO 항목을 끝내면 ☑ 하고, 필요하면 `다음 작업`이 그다음 미완 항목을 가리키게 갱신한다.
  - feature에 **전용 `HARNESS.md` 로드맵**(예: item의 S1~S10)이 있으면 그것이 세부 TODO 역할을 하므로, progress의 `## 세부 TODO`는 그 로드맵을 **가리키기만** 하고 중복 나열하지 않는다.
  - 이 세부 TODO는 feature 내부 작업용이다. feature와 무관한 잡다한 할 일은 여기가 아니라 `TODO-BOARD.md`(§7)에 둔다.
- **작업 로그는 feature 폴더의 `worklog.md`에 별도 보관**한다 (progress엔 `## 작업 로그` 헤더 + 포인터 링크만). 로그는 계속 자라는 아카이브라 매 세션 재로드 비용을 분리하려는 것 — 재개 앵커는 progress `## 다음 작업`이다. worklog는 **최신이 위로** 쌓는다.
- 로그는 "무엇을 왜 했는가" 중심으로 3~7줄 이내로 요약한다. 코드 전문을 붙여넣지 않는다.
- `결정 기록` **상세는 feature 폴더 `decisions.md`**에 둔다(§8 품질 기준: 맥락·대안·근거·결과·재평가 트리거). progress `## 결정 기록`엔 **요지 인덱스 + 링크만** (worklog와 같은 이유로 분리 — 해당 영역 건들 때 decisions.md 확인). 트레이드오프가 있었던 결정만, 사소한 네이밍 등은 제외.
- **식별 코드:** 각 결정엔 feature 내 고유한 `D1`·`D2`…(순번, 재번호·재사용 금지)를 부여한다. decisions.md와 progress 인덱스가 같은 ID를 공유하고, worklog·`다음 작업`에서 결정을 가리킬 땐 `(→D3)`처럼 코드로 링크한다. 로드맵 슬라이스(`S#`/`I#`/`E#` 등)도 worklog에서 같은 방식으로 참조해 **"언제(worklog) → 무슨 작업(S/I/E) → 왜(D)"**가 코드로 이어지게 한다.
- **`최종 갱신`은 날짜+시각**(`YYYY-MM-DD HH:MM`, KST)으로 적고, 문서를 바꿀 때마다 현재 시각으로 갱신한다 — 하류 문서(architecture·wiki) 동기화 판별의 기준(§3.4).
- `다음 작업`은 항상 **실행 가능한 수준**으로 구체화한다.
  - 나쁜 예: "전투 시스템 개선"
  - 좋은 예: "`AttackState.cs`에 콤보 입력 버퍼(0.3s) 추가 후 `PlayerStateMachine` 전이 연결"

## 6. Feature 생성 / 완료 / 폐기 절차

### 신규 feature 등록
1. `feature-list.md`에 행 추가 (`📋 PLANNED`)
2. `feature/<feature-id>/` 폴더를 만들고, 템플릿 기반으로 `progress.md` 생성 (구현 방향·불변 조건·로드맵이 방대하면 같은 폴더에 `HARNESS.md`도 작성)
3. `목표`, `수용 기준`, `범위`를 반드시 채운 후 작업 착수

### 완료 처리
1. `수용 기준` 전 항목 체크 확인
2. progress 상태 → `✅ DONE`, 최종 로그 기록
3. `feature-list.md` 상태 동기화
4. **wiki 갱신 리마인드(마일스톤):** feature를 `✅ DONE` 처리했으면, 포트폴리오 wiki(`wiki/`)가 낡았을 수 있음을 유저에게 **한 줄 리마인드**한다. — wiki를 직접 고치지는 않는다(갱신은 요청 시에만; `wiki/HARNESS.md` §0). 어긋날 만한 섹션이 짐작되면 함께 짚어준다. (예: "item-system 완료 — wiki의 `arch`/`todo` 섹션이 코드와 어긋날 수 있으니 갱신할까요?")

### 폐기/통합 처리
1. progress 최상단에 폐기 사유 및 (통합 시) 대상 feature-id 기록
2. 양쪽 문서 상태를 `🗄️ ARCHIVED`로 동기화

## 7. 작업 보드 (TODO-BOARD.md)

`feature-list.md`가 **feature 단위**를 추적하는 반면, `TODO-BOARD.md`는 그보다 **잘게 쪼개진 잡다한 작업·개인 TODO·이슈**를 모으는 별개 레이어다. (문서 정비, 인프라, 실험, 리팩터, 아이디어 등 feature로 묶기 애매한 것)

### 7.1 구조
- 상태 3칸 고정: `## 📋 TODO` → `## 🔧 진행 중` → `## ✅ Done`. 항목은 상태가 바뀌면 해당 칸으로 **이동**한다(복제 금지).
- 항목 형식: `- [ ] **(범주)** 내용 — 비고 _(YYYY-MM-DD 등록)_`. 완료 시 `- [x]` + 완료일. 범주 예: `wiki`·`docs`·`infra`·`bug`·`idea`.
- 각 칸이 비면 `(없음)`으로 명시한다.

### 7.2 유지 규약 (반자동 — 훅 아님)
- **세션 시작 시** 이 보드를 한 번 훑는다(`진행 중`에 걸린 게 있는지 확인).
- **포착:** 채팅·작업 중 할 일/이슈/아이디어가 나왔는데 보드에 없으면 → 그 자리에서 `📋 TODO`에 추가한다. (사용자가 명시적으로 지시하지 않아도, 놓치지 않게 잡아 둔다)
- **상태 전이:** 어떤 항목에 착수하면 `🔧 진행 중`으로, 끝나면 `✅ Done`(완료일 기입)으로 옮긴다.
- feature 단위로 커진 항목은 보드에서 빼고 `feature-list.md`에 등록한다(중복 추적 금지).
- 상단 `최종 갱신` 날짜를 바꿀 때마다 갱신한다.

## 8. 포트폴리오·면접 대비 (산출물 기준)

평가 대상은 **코드의 양이 아니라 판단의 질 + 굴러가는 데모**다. 면접·포트폴리오가 실제로 검증하는 건 "무엇을 만들었나"보다 **"왜 그렇게 결정했고, 어떤 대안을 두고 무엇을 포기했나"**이므로, 모든 작업은 아래를 산출물로 남긴다. (판단이 문서화 안 된 코드는 산출물로 인정하지 않는다 — §1)

### 8.1 결정 기록 품질 기준

트레이드오프가 있는 결정은 feature 폴더 `decisions.md`에 아래를 담아 **상세히** 남긴다 (progress `## 결정 기록`엔 요지 인덱스 + 링크만 — §5). 표 `채택 사유` 칸에 서술로 압축, INV 관련 결정은 근거에 INV-ID 명시. (자명한 선택·네이밍은 제외 — 과잉 기록은 유지 부담)

- **맥락(forces):** 왜 이 결정이 필요했나 — 충돌한 제약·요구.
- **대안:** 진지하게 검토한 후보 + 각 장단 (버린 것도 이유와 함께).
- **근거:** 왜 이걸 택했나, 그리고 **왜 대안이 아니었나**.
- **결과·트레이드오프:** 무엇을 얻고 **무엇을 포기했나** — 부정적 결과를 반드시 포함.
- **재평가 트리거:** 이 결정을 뒤집을 조건 (예: item의 "복수 부위 점유 시 `SlotType[]` 확장").

### 8.2 "왜"의 품질 — 기술 주장이 아니라 결과·맥락에 연결

면접에서 트레이드오프 서술은 시니어급일수록 가장 무겁게 채점된다. 다운사이드를 인정하는 게 성숙함의 신호이고, 단점 없는 선택처럼 쓰면 판단을 안 한 것으로 읽힌다.

- ❌ 약함: "캐시가 더 빠르니까" (맥락 없는 기술 진술)
- ✅ 강함: "읽기 지연은 줄지만 최종 일관성을 감수 — 이 기능은 신선도보다 속도가 중요해 허용"
- 기준: **한 결정을 한 문장으로 "왜"까지 말할 수 있어야 한다** (CLAUDE.md 개발 방향). 말이 막히면 근거가 부족한 것.

### 8.3 데모·서사

- **굴러가는 데모:** 슬라이스는 완료 시 에디터에서 눈으로 확인 가능해야 한다 (수직 슬라이스; feature 로드맵이 있으면 그것). "아름다운 설계"가 아니라 **"굴러간다 + 왜 이렇게 했는지 설명된다"**가 완성.
- **서사:** `worklog.md`는 시간순 "판단의 이야기"로 읽히게 쓴다 — 무엇을 왜 했고, 어디서 막혀 어떻게 풀었나. 리뷰는 과정 나열이 아니라 스토리를 본다.
- **절제도 산출물:** 과설계는 감점이다. "필요 없지만 인상적이라 추가" 금지, 절제한 판단(왜 단순한 쪽을 택했나)도 기록 대상이다 (북극성).

## 9. 금지 사항

- ❌ progress 갱신 없이 세션 종료
- ❌ `feature-list.md`와 progress 상태 불일치 방치
- ❌ 등록되지 않은 feature에 대한 구현 착수
- ❌ 다른 feature의 progress를 해당 feature 세션 외부에서 무단 수정
- ❌ 작업 로그에서 과거 기록 삭제/수정 (오기 정정 시 취소선 + 정정 표기)
