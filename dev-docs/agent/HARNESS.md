# HARNESS.md — Agent 작업 규약

> 이 문서는 **feature 현황 추적과 세션 작업 프로토콜**을 정의한다. 진입점은 루트의 `CLAUDE.md`이며, 실제 구현 작업(feature 착수·진행·완료)에 들어가기 전 이 문서를 읽는다.
> 에이전트 작업 문서는 전부 `dev-docs/agent/`에 있다.

---

## 1. 핵심 원칙

1. **문서가 곧 상태(State)다.** Agent의 컨텍스트는 세션마다 초기화된다. 세션 간 유일한 기억은 `dev-docs/` 문서이므로, 문서에 기록되지 않은 작업은 없었던 작업으로 간주한다.
   - **작업 규약·소통 방식·재발 방지 지침은 개인 메모리가 아니라 이 하네스(또는 관련 `dev-docs/` 문서)에 적는다.** 개인 메모리는 리포지토리 밖의 사적 설정일 뿐이라, 이 프로젝트의 규약은 리포에 함께 버전관리되는 하네스가 진실의 출처여야 한다(포트폴리오·협업 대상). "이건 앞으로 이렇게 해라"류 지시를 받으면 메모리에 남기지 말고 하네스에 규칙으로 넣는다. (2026-08-04 유저 지시)
2. **읽기 → 작업 → 기록.** 모든 세션은 이 3단계를 따른다. 기록 없이 세션을 종료하지 않는다.
   - **기록은 세션 끝에 몰아서 하는 절차가 아니라 습관이다 — 의미 있는 진전(결정·구현·에셋 변경)이 생길 때마다 그 자리에서 즉시 남긴다.** 유저가 "문서 써라"라고 지시하기를 기다리지 않는다. **시키지 않아도 버릇처럼 남긴다.**
   - 이유: 세션은 **예고 없이 끊긴다.** 유저가 기록을 지시하지 않고 닫는 경우가 많고(유저가 그렇다고 밝힘), 그러면 §3.3 종료 절차가 **아예 실행되지 않는다.** 증분 기록이면 그 시점에 이미 문서가 최신에 가까워 유실이 최소화된다 — 종료 절차는 "마지막 정리"이지 "유일한 기록 기회"가 아니어야 한다.
   - 우선순위: 진전이 있을 때마다 최소한 **`NOW.md`(재개 지점)**를 먼저 손보고, 결정이면 `decisions.md`(§3.2), 구현이면 `worklog.md`/progress를 그 흐름에 이어 남긴다. 한 턴이 커지면 중간에도 남긴다(§3.2 "컨텍스트가 길어지면 중간 요약").
   - ⚠ 한계: 이건 **텍스트 규약**이라 세션이 강제 종료되면 이 규약 자체도 못 켜진다. 종료 시점 자동 리마인드가 필요하면 **Stop 훅**(`.claude/settings.json`)이 더 확실하다 — 원하면 유저가 요청.
3. **하나의 세션, 하나의 feature.** 한 세션에서는 원칙적으로 하나의 feature에만 집중한다. 다른 feature의 코드를 수정해야 한다면 해당 feature의 progress에 사유를 기록한다.
4. **추측 금지.** progress 문서와 실제 코드가 불일치하면, 코드를 진실로 보고 progress 문서를 수정한 뒤 작업을 시작한다.
   - **문서 기록은 과거 시점의 스냅샷이다.** `NOW.md`·progress·worklog에 적힌 상태를 **현재 상태로 단정하지 않는다.** "지금 어떠하다"고 말하기 전에 **실물(코드·에셋·git)을 확인**한다. 문서가 낡았을 가능성이 기본값이다.
     > 2026-07-20 실제 발생 — NOW.md의 옛 기록(`GE_TestSpeedUp` 배선 없음)을 보고 "`GE_Speed`에 Execution 배선이 안 돼 있다"고 단정했으나, 실제 에셋에는 이미 배선돼 있었다. 다른 에셋의 과거 기록을 현재 에셋 상태로 옮겨 읽은 것.
5. **에이전트의 판단은 틀릴 수 있다.** 아래 §1.1.

### 1.1 에이전트의 판단은 틀릴 수 있다 — 항상 인지한다

**AI의 판단·설명·기억에는 실수와 오류가 섞인다.** 이건 예외적 사고가 아니라 상시 조건이다. 에이전트는 자기 출력을 항상 "틀렸을 수 있는 것"으로 다루고, 유저도 그렇게 다룰 수 있게 **근거와 확신도를 드러내야** 한다.

실무 규칙:

1. **주장과 근거를 분리해 말한다.** "X다"가 아니라 "**무엇을 보고** X라고 판단했는지"를 같이 낸다 — 읽은 파일·줄 번호, 실행한 명령, 검색한 출처. 근거를 못 대면 그건 주장이 아니라 추측이다.
2. **확신도를 구분해 표기한다.** 직접 확인한 것 / 근거는 있으나 불확실한 것 / 모르는 것을 뭉뚱그리지 않는다. 특히 **직접 읽은 코드**(확정)와 **외부 API·엔진 동작에 대한 기억·2차 자료**(불확실)를 같은 어조로 말하지 않는다.
   - **트리거 — 엔진·외부 API 동작을 묻는 질문("UE는 어떻게 하나", "이 엔진/라이브러리가 X를 어떻게 처리하나" 류)을 받으면, 답 문장을 쓰기 전에 멈추고 원문부터 확인한다.** 기억·2차 자료(포럼 글·블로그·WebFetch 요약 등)로 **먼저 답하지 않는다.** "대체로 이렇다"는 초안이 머릿속에 있어도, 그걸 내보내기 전에 원문(ylyking UE 미러·Epic 문서·해당 라이브러리 소스)을 연다. 이건 §8.5(UE 원본 확인)의 **실행 단계**다 — §8.5는 "근거로 무엇을 대나", 이 트리거는 "답하기 전 언제 멈추나"를 정한다.
     - WebFetch/검색 **요약도 2차 자료다.** 큰 파일은 요약이 분기·중첩을 오독할 수 있으니, 결론이 걸린 지점은 원문 코드 라인을 직접 본다(§1.2).
     > 2026-08-05 실제 발생 — "period 0 Duration/Infinite에서 Execution이 도는가"에 **기억으로 먼저 설명**했다(유저: "기억으로 확인할 문제 아냐"). 이후 UE 소스를 직접 받아 `check()` assert 라인까지 확인해 결론은 맞췄지만, **답부터 나간 것**이 문제. 같은 유형이 2026-07-19·08-04에도 반복(§1.2 사례).
3. **모르면 모른다고 한다.** 그럴듯한 답을 채우지 않는다(§8.4와 같은 뿌리).
   - **값·식별자를 지어내지 않는다.** GUID·fileID·경로·파일명·버전·날짜 등은 **실제 값을 조회해서** 쓴다. 형식만 맞는 그럴듯한 값을 임시로 채워 넣지 않는다 — 파일에 한 번 들어가면 진짜와 구분되지 않는다.
     > 2026-07-20 실제 발생 — 프리팹의 `effect` 참조에 임의 GUID를 지어내 넣었다(직후 실제 값으로 교체). 에셋 참조가 조용히 깨지는 종류의 실수다.
4. **반박당하면 방어부터 하지 않는다.** 유저가 다른 정보를 제시하면 **내 근거의 강도부터 다시 본다.** 근거가 약했으면 그 자리에서 인정하고 정정한다. 근거가 충분하면 그 근거를 제시해 대조한다 — 어느 쪽이든 "누가 맞나"가 아니라 "무엇으로 가릴 수 있나"로 옮긴다.
5. **한 번 틀린 종류는 기록한다.** 반복되는 실수 유형은 개인의 부주의가 아니라 빠진 규약이다(§3.3.2).
6. **해석할 때 일반화·섣부른 판단 금지.** 아래 §1.2.

### 1.2 해석 규율 — 일반화·섣부른 판단 금지

자료(문서·검색 결과·코드·유저 발언)를 **해석**하는 순간이 가장 틀리기 쉬운 지점이다. 관측한 범위를 넘어 결론을 넓히지 않는다.

- **사례 1건을 일반 규칙으로 만들지 않는다.** "포럼 글 하나에서 이랬다" → "원래 그렇다"로 넘어가지 않는다. 표본이 하나면 표본이 하나라고 말한다.
- **중의적 문장에서 한 해석을 골라 사실로 굳히지 않는다.** 두 가지로 읽히면 **두 가지로 읽힌다고 말하고** 가릴 방법을 제시한다. 골라 놓고 그게 원문인 것처럼 전달하지 않는다.
- **부분 관측을 전체 동작으로 확대하지 않는다.** 한 경로에서 확인한 것이 다른 경로에서도 같으리라고 가정하지 않는다. 확인한 경로를 명시한다.
- **표면이 비슷하다고 같은 것으로 취급하지 않는다.** 이름·용어가 같아도 계층·의미가 다를 수 있다(예: Unity `CharacterController` ≠ UE `CharacterMovementComponent` — 대응 계층이 다르다).
- **"아마 이럴 것이다"를 근거 없이 결론으로 쓰지 않는다.** 추론은 추론이라고 표시하고, 확인 가능하면 확인한다(§1.1-1).
- **유저가 원하는 결과·목표를 확인하기 전엔 어떤 방향을 "필요/불필요"로 세게 단정하지 않는다.** 특히 "과설계니 하지 말자"·"이건 필요 없다"류 가치판단은 유저 의도(1순위)를 먼저 물어 확인한 뒤에 낸다. 기술적으로 "지금 불필요"해 보여도, 그건 *유저가 무엇을 원하는지*에 종속된 판단이라 목표가 확정되기 전엔 성립하지 않는다. (설계 트레이드오프 제시까지는 하되, 결론을 미리 못박지 않는다.)

판단이 필요한 순간에 스스로 묻는다: **"내가 실제로 본 것은 어디까지이고, 어디부터가 내 추론인가?"** 그리고 **"이 '필요/불필요' 판단이 유저가 확인해 준 목표 위에 서 있나, 아니면 내가 목표를 지레짐작한 건가?"**

> 2026-07-20 실제 발생 — Epic 문서의 중의적 한 문장을 한쪽으로만 읽고, 포럼 글 1건을 더해 "UE도 같습니다"라는 일반 진술로 확대했다. 결과적으로는 맞았으나 **당시 근거로는 도출할 수 없는 결론**이었다.

> 2026-07-20 실제 발생 — GE Execution이 Duration/Infinite + period 0에서 실행되는지를 두고, 근거가 **포럼 글 1건**뿐인데 "UE도 같습니다"라고 단언했다. 유저가 반대 자료를 제시해 재확인하니 Epic 문서 원문이 중의적이어서 **양쪽으로 읽히는 문장**이었고, 결정적 근거인 UE 소스는 확인 수단이 없었다. 직접 읽은 이 프로젝트 코드(확정)와 UE 동작에 대한 2차 자료(불확실)를 같은 어조로 말한 것이 문제였다.

> 2026-08-07 실제 발생 — aggregator(어트리뷰트 반응성) 도입을 두고, 유저 목표를 확인하기 전에 "지금은 불필요(과설계)"라고 세게 추천했다. 정작 유저가 원한 건 라이브 재평가여서 방향이 뒤집혔다. "필요 없다"는 기술 판단이 *유저가 무엇을 원하는지*에 종속인데, 목표를 지레짐작하고 결론부터 낸 것이 문제였다.

## 2. 디렉토리 구조

```
dev-docs/
├── agent/                      # 에이전트 작업용 (본 규약이 관리하는 대상)
│   ├── HARNESS.md              # 본 문서 (프로세스 규약: feature 추적·세션 프로토콜)
│   ├── NOW.md                  # 단일 재개 지점 — "지금 뭐 하던 중이었나" 임시 메모 (§2.1·§3.1)
│   ├── feature-list.md         # 전체 feature 목록 및 상태 대시보드
│   ├── TODO-BOARD.md           # 잡다한 작업·개인 TODO·이슈 보드 (feature-list와 별개 레이어; §7)
│   └── feature/
│       ├── <feature-id>/           # 단일 feature (그룹 불필요 시)
│       │   ├── progress.md          # 진행 문서 (필수)
│       │   ├── worklog.md           # 작업 로그 (아카이브; progress에서 분리 — §5)
│       │   ├── decisions.md         # 결정 기록 상세 (progress엔 요지 인덱스 — §5·§8)
│       │   └── HARNESS.md           # feature 전용 하네스/설계·기획 문서 (선택)
│       └── <group-id>/             # feature 그룹 (대분류; 하위 feature가 많을 때 묶는다)
│           ├── HARNESS.md           # 그룹 공유 하네스/설계 (선택, 하위 전체를 지배)
│           └── <feature-id>/        # 하위 feature
│               ├── progress.md      # 진행 문서 (필수)
│               ├── worklog.md       # 작업 로그 (아카이브; §5)
│               └── decisions.md     # 결정 기록 상세 (§5·§8)
└── project/                    # 프로젝트 자료 (작업 규약 대상 아님)
    ├── design.md               # 게임 기획
    ├── CODE_CONVENTION.md      # 코드 컨벤션
    ├── dev-tools.md            # 개발 도구 설정
    └── architecture/           # 시스템 구조·설계 문서
```

- feature-id·group-id는 **kebab-case 영문 소문자**로 짓는다. (예: `combat-core`, `enemy-ai`, `item-system`)
- 각 feature는 폴더를 가지며 진행 문서는 반드시 그 안에 `progress.md`로 둔다. 단일 feature는 `feature/<feature-id>/`, 그룹 하위 feature는 `feature/<group-id>/<feature-id>/`.
- **그룹(대분류):** 한 도메인의 하위 feature가 여러 개로 늘어 대시보드 가독성이 떨어지면 `feature/<group-id>/`로 묶는다. (예: `item-system` → `item`·`inventory`·`equipment`, `ability-system` → `gameplay-effect`·`attribute`) 그룹 자체는 progress를 갖지 않으며, 하위 feature 전체를 지배하는 **공유 불변조건·설계**가 있으면 그룹 폴더에 `HARNESS.md`를 둔다(하위 feature는 이를 참조하고 중복 정의하지 않는다).
- feature 고유의 **구현 방향·불변 조건·로드맵 또는 설계/기획**이 방대하면 같은 폴더에 `HARNESS.md`(feature 전용 하네스/설계 문서)를 둔다. 본 문서(일반 HARNESS)는 **프로세스 규약**, feature/그룹 `HARNESS.md`는 **그 feature의 구현 규약/설계**로 역할이 다르다. 충돌 시 일반 HARNESS의 프로세스 규약이 우선하되 충돌을 보고한다.
- `feature-list.md`에 없는 feature의 폴더를 만들지 않는다. (등록이 먼저다)

### 2.1 NOW.md — 무엇인가 (성격 정의)

**위치: `dev-docs/agent/NOW.md`.** 세션 재개 시 여기서 확인한다.

**NOW.md는 말 그대로 "지금 뭐 하던 중이었더라"를 더듬기 위한 임시 메모다.** 정식 기록물이 아니라 **휘발성 작업 메모**이며, 다음 성격을 갖는다.

- **임시·덮어쓰기 대상:** 매 세션 종료 시 현재 상태로 **통째 다시 쓴다**(§3.3-1). 이력을 쌓지 않으며, 과거 내용을 보존할 의무가 없다 — 이력은 `worklog.md`, 판단은 `decisions.md`, 상태는 progress/feature-list가 담당한다.
- **진실의 출처가 아니다:** 내용이 progress·코드와 어긋나면 **NOW.md가 틀린 것**이다(§1-4 추측 금지와 동일 기준). NOW.md는 "어디서 멈췄나"를 가리키는 포인터일 뿐, 설계·상태의 근거로 인용하지 않는다.
- **그래서 짧게:** 지금 할 일 / 멈춘 지점 / 선행조건 / 미정 항목 정도. 여기에 설계 논의·결정 근거를 쓰기 시작하면 자리를 잘못 잡은 것이다 → 해당 문서로 옮긴다.
- **대신 재개에 필요한 건 빠짐없이:** 다음 세션이 NOW.md만 읽고 즉시 움직일 수 있어야 한다(§3.1). 특히 **외부 선행조건**(Unity 에디터·MCP·에셋 배선 등)과 **승인 안 난 산출물**(§3.3.1)은 반드시 명시해, 다음 세션이 재발견하거나 기정사실로 취급하지 않게 한다.

## 3. 세션 프로토콜 (Agent 필수 절차)

### 3.1 세션 시작 시 (이어하기)

**단일 재개 지점은 `NOW.md`다.** 유저가 "하던거 하자"류로 이어하기를 요청하면 — 또는 세션을 그냥 이어가면 — **`NOW.md` 하나만 읽고 곧장 `## ▶ 지금 할 일`부터 실행한다.** 이게 목적이자 규칙이다: **전부 확인하지 말고 명확·빠르게 재개한다.**

- feature-list·progress·worklog·코드를 **미리 훑지 않는다.** (TODO-BOARD는 예외 — §7.2에 따라 세션 시작 시 한 번 훑는다) NOW.md가 지목한 액션을 바로 하고, 막히거나 더 깊은 맥락이 필요할 때만 NOW.md에 걸린 링크(해당 feature progress 등)를 연다.
- IN-PROGRESS feature가 여럿이어도 **어느 걸 이어할지 고민하지 않는다** — NOW.md가 지목한 하나가 진실이다.
- NOW.md의 선행조건(예: Unity MCP)이 안 갖춰졌으면, NOW.md에 적힌 대안/요청을 그대로 따른다(예: "에디터 열고 세션 재시작" 1줄 요청 후 대기).
- 유저 지시가 NOW.md와 다르면 **유저 지시가 우선**. 그 지시가 새 초점이면 NOW.md를 그 자리에서 갱신하고 진행한다.

> feature-list(현황 대시보드)·TODO-BOARD(잡다한 backlog)·progress(feature 상세)는 각자 역할이 있지만 **재개 메커니즘이 아니다.** 재개는 오직 NOW.md.

### 3.2 작업 중

> **이 절은 "이어하기"뿐 아니라 직접 요청("~구현해줘")으로 시작한 feature 코드 작업에도 똑같이 적용된다.** §3.1은 "빠르게 재개(미리 훑지 말라)"를 강조하지만, 그 행동 편향은 **재개 방식**에 대한 것이지 **기록 생략**의 근거가 아니다. 코드를 건드리기 시작하는 순간 아래 즉시-기록 규율이 켜진다.

- **설계 결정(트레이드오프가 있는 선택)을 내리면 그 결정을 구현한 편집과 같은 턴에, 늦어도 다음 코드 편집을 하기 전에 기록한다** — feature 폴더 `decisions.md`에 상세 + progress `## 결정 기록`에 요지 한 줄. **세션 종료(§3.3)까지 미뤄 몰아 쓰지 않는다.** "즉시"의 앵커 = *다음 코드 편집 직전*. 여러 결정을 세션 끝에 한꺼번에 적고 있다면 이미 규율을 어긴 것이다. **품질 기준은 §8** (포트폴리오·면접 산출물이므로 상세히). ("무엇을 안 만들기로 했나"=절제·생략 결정도 트레이드오프 결정이므로 동일하게 즉시 기록 — §8.3.)
- **문서·파일을 지우거나 옮기면, 그것을 가리키는 곳을 같은 턴에 고친다.** 삭제·이동·이름 변경 직후 링크와 경로 언급을 검색해(`grep`으로 파일명·경로) 전부 갱신한다. 나중으로 미루면 죽은 링크가 남고, 다음 세션은 그 링크를 **존재하는 문서로 믿고** 열려다 헤맨다. 참조처가 많아 비용이 커지면 §3.2의 "토큰 큰 작업" 규칙대로 먼저 알린다.
  - *사례(2026-07-19):* `feature-progress-TEMPLATE.md`를 지우면서 §2 트리·§6 절차의 참조를 같이 고쳤다. 반면 item-system 문서를 `archive/`로 옮겼던 2026-07-18 작업은 그러지 않아 `feature-list.md`의 링크 4개가 죽은 채 남았다.
- 작업이 막히면(외부 의존성, 미확정 스펙 등) `## 블로커`에 기록하고 사용자에게 보고한다.
- feature 범위가 커지면 임의로 확장하지 않고, 분리 제안을 사용자에게 보고한다.
- 컨텍스트가 길어지면 세션 종료 전이라도 `worklog.md`·progress `## 다음 작업`에 중간 요약을 남긴다. (컨텍스트 압축·리셋으로 진행 내용이 유실되지 않게)
- 문서(특히 하네스·decisions·worklog)에 **유저 의도를 넘어선 각색·해석·함의**를 남기려 하면 — 금지가 아니라 — **쓰기 전에 무조건 유저에게 먼저 묻는다.** 물어서 승인되면 남겨도 된다. 기록의 기준은 유저의 의도다.
- **토큰(컨텍스트)이 크게 나갈 작업은 착수 전에 규모·방식을 먼저 묻는다.** 도구 호출·조회가 여러 번 반복될 게 예상되는 작업 — 광범위 참조 추적, 정합성 검증(주석/코드 구분·using 파급 등), 다수 파일 일괄 편집, 대규모 리팩터 — 은 바로 시작하지 말고 예상 비용을 알리고 **범위 축소·검증 위임 옵션**을 제시한 뒤 진행한다. (예: "범위를 X만으로 좁힐까", "컴파일 검증은 유저가 Unity에서 볼까".)
  - *사례(2026-07-08):* 에디터 스크립트 feature-local `Editor/` 통일 + `EquipmentComponent`·`IEquippable`·`SlotType`을 `Core.ItemSystem.Equipment`로 승격. namespace 12+파일 변경 자체는 작았으나, **컴파일을 유저가 하는 구조라 참조 정합성을 코드로 직접 검증**(참조처 grep을 주석/코드까지 구분, 파일별 using 파급 추적, 이동 후 잔재 검증)하느라 조회가 크게 나갔다. 착수 전 "이만한 검증 비용이 든다 — 범위를 좁힐지, 컴파일은 Unity에서 확인할지"를 먼저 물었어야 한다.
- **대화의 스코프를 벗어나지 않는다 — 물어본 것에만 답한다.** "X가 뭐야", "UE는 어떻게 해", "이거 맞아?"는 **설명 요청**이지 제안·계획·착수 요청이 아니다. 설명하고 멈춘다. 다음을 답변에 끼워 넣지 않는다:
  - **요청하지 않은 추천·계획·"이렇게 할까요?"** — 유저가 필요하면 스스로 묻는다. 매번 붙이면 설명 하나가 결정 요구로 바뀌어, 유저가 원치 않는 판단을 계속 하게 만든다.
  - **지금 주제 밖의 시스템·파일·결정** — 특히 파킹된 영역(NOW.md `🅿`)은 유저가 먼저 꺼내기 전엔 언급도 하지 않는다.
  - **이미 결론난 결정을 미결처럼 되살리기** — `decisions.md`에 근거와 함께 남긴 선택(D#)을 "빠진 것"으로 다시 올리지 않는다. 뒤집을 조건은 그 결정의 *재평가 트리거*(§8.1)이지, 대화 중 임의 재론이 아니다.
  - **요청된 축을 넘는 비교** — 비교·분석을 요청받아도 유저가 지목한 축만 본다. 스코프 밖 항목(미도입 결정분·애초에 범위 밖인 기능)을 결함처럼 나열해 "빠진 게 많다"는 그림을 만들지 않는다.
  - **과한 길이** — 답변 분량도 스코프다. 한 줄 질문에 다중 섹션 문서로 답하면 실제 답이 묻히고, 곁가지가 새 논점을 만든다.
  - *사례(2026-07-19, GAS Execution):* ① "capture가 뭐야"·"UE는 어떻게 해" 같은 설명 요청마다 끝에 추천과 "구현할까요?"를 붙여 매번 결정을 요구했다. ② "왜 에셋 형태냐"에 답하다 대안 패턴을 찾겠다고 **파킹된 item-system**을 끌어왔다. ③ "Execution 하자"를 착수 지시로 읽고 요청에 없던 `defense` 어트리뷰트 신설·ASC 동작 변경까지 했다(→ [[discuss-before-implement]] 계열). ④ UE 대비 표에 캡처(당시 **유보로 기록해둔 항목**)·네트워크·태그·채널을 ❌로 나열해, 유저 관심사(현재 있는 Modifier/Execution의 순서·결과값)와 무관한 "기본이 빠졌다" 논점을 만들었다. 유저: "괜히 쓸데없이 과하게 뭐 하고 있잖아."
- **설계 논의 중에는 구현에 착수하지 않는다 — 제안까지만.** 유저가 설계에 의문을 제기하거나("납득 안 돼", "왜 이렇게 하지?") 방향을 논의 중일 때, 방향이 그럴듯해 보인다고 동의를 얻은 것으로 판단하지 않는다. 구조 스케치·트레이드오프까지 내놓고 **"이 방향으로 구현할까?"에서 멈춘다.** `구현해줘`·`해봐`·`가자` 같은 **명시적 착수 지시**가 있을 때만 파일을 만든다.
  - **순서 합의 ≠ 착수 지시.** "다음엔 X 하자"는 *무엇을 할지*의 합의지 *지금 쓰라*는 지시가 아니다. 그 턴에도 구체안을 제시하고 한 번 더 멈춘다.
  - **착수 지시를 받았어도 범위는 지시된 것만.** 구현 중 없는 것(필드·API·에셋)을 발견하면 그게 곧 **멈추고 물을 지점**이다. 특히 **데이터 모델 변경·기존 동작 변경은 항상 별도 승인 대상**. "문서에 적힌 목표 시나리오니 스코프 확장이 아니다"류의 자기 정당화가 나오면 그 자체가 위반 신호다.
  - 발견한 버그·개선점은 **고치지 말고 보고만** 한다(§3.5.4).
  - *사례(2026-07-09, Strategy 리팩터):* 유저가 설계에 의문을 제기하는 중에 코드를 쓰기 시작해 중단당했다. *사례(2026-07-19, GE Execution):* "이후에 Execution 하자"를 착수 지시로 읽고 요청에 없던 `CombatAttributeSet.defense` 신설·ASC 가드 동작 변경·`DamageExecution` SO 신규까지 한 번에 작성 — 유저: "뭘 멋대로 하고 있어 / 내가 시키기 전에 하지 말라고."
- **공통화는 사용처 수로 크기를 정한다 — 2+면 최소 조각이 아니라 통째로 묶은 편의 API.** 사용처가 하나뿐이면 최소로 간다(§8.3 절제). 하지만 **이미 중복 사용처가 둘 이상**이면 추상화가 정당하므로, 작은 primitive만 뽑아 호출부에 보일러플레이트를 남기지 말고 **생성·삽입·갱신·빈 상태 처리까지 흡수한 상위 헬퍼**를 처음부터 제안한다. 차이 나는 부분만 콜백/파라미터로 노출한다.
  - *사례(에디터 드로어 리팩터):* 팝업 util(`TypeAddMenu`)만 뽑았다가 "작은 util 말고 크게 묶어서 편하게 쓰게 해봐" 지적을 받고, 리스트 배선까지 감싼 `TypeChoiceList.Create`로 만들자 "처음부터 이랬으면"이라는 반응. 유저가 "더 크게"를 다시 요청하게 만들지 않는다.
- **좁은 스코프·가정 위에서만 성립하는 구현은, 그 한정성을 스스로 표면화해 착수 전에 확인한다.** 설계 제약·스코프·정책이 여러 갈래로 갈리면 — 특히 "어디까지를 한 단위/스코프로 볼지", 되돌리기 비용 있는 데이터·구조 선택, 동작 정책(우선순위·중복 처리·기본값 등) — 한 쪽을 임의로 정하지 말고 유저에게 제시해 확정받는다. **갈림이 겉으로 드러나지 않아도**, 내가 특정 좁은 상황에서만 동작하도록 구현하려 하면 그 가정을 먼저 밝혀 확인한다(유저가 나중에 "그럼 X는?" 하고 지적하기 전에 스스로). 이미 짜기 시작했어도 한정성이 보이면 멈추고 묻는다.
  - *사례(2026-07-08):* `SubclassSelector`의 중복 제외(`uniqueInList`)를 **"자기가 속한 리스트만 스캔"** 이라는 좁은 스코프로 조용히 구현했다. 유저가 "리스트 외부는?"이라 물어서야 그 한정성이 드러났다 — 유일성 스코프(자기 리스트 / 같은 오브젝트 전체 / 커스텀 태그 그룹 / 프로젝트 전역)는 수집 방식·비용·규약이 전혀 달라 처음부터 "이 구현은 리스트 내부 한정인데 그 범위면 되냐"를 밝히고 물었어야 했다.

### 3.3 세션 종료 시 (필수)

1. **`NOW.md`를 다음 재개 지점으로 갱신한다 (최우선).** 이번 세션 종료 시점 기준으로 `## ▶ 지금 할 일`(feature + 다음 액션)과 `## ⚙ 선행조건`을 다시 쓴다. — **다음 세션이 NOW.md만 읽고 즉시 재개할 수 있어야 한다.** 액션이 외부 선행조건(Unity MCP 켜짐·에디터 열림·세션 재시작·특정 에셋 등)을 요구하면 반드시 여기 명시(다음 세션이 재발견하지 않게).
2. feature 폴더의 `worklog.md`에 오늘 날짜로 수행한 작업을 요약 기록한다. (로그는 아카이브라 progress.md에서 분리 — §5)
3. 해당 feature progress의 `## 다음 작업`을 갱신한다. (NOW.md는 "지금 하나", progress `## 다음 작업`은 그 feature의 이후 순서 — 둘이 어긋나지 않게)
4. feature 상태가 변했으면 progress 상단의 상태와 `feature-list.md`의 상태를 **둘 다** 갱신한다. (단일 갱신 금지 — 항상 동기화)
5. **`TODO-BOARD.md`를 갱신한다** (§7.2). 이번 세션에 착수/완료한 항목을 해당 칸으로 옮기고, 대화 중 새로 나온 할 일을 `📋 TODO`에 포착한 뒤 상단 `최종 갱신`을 고친다.
6. **세션 회고를 유저에게 보고한다** (§3.3.1).
7. **하네스 자체를 점검한다** (§3.3.2).

#### 3.3.1 세션 회고 — 문제가 있었던 지점 보고

세션을 마무리할 때, **이번 세션에서 잘못했던 것을 스스로 짚어 보고한다.** 유저가 지적하기를 기다리지 않는다.

- **대상:** 규약 위반 / 요청 범위를 벗어난 작업 / 잘못된 판단·추측 / 유저가 교정해준 지점 / 승인 없이 만든 코드·문서.
- **형식:** "무엇을 · 왜 그렇게 됐는지 · 어디에 남길지" 세 줄. 요약으로 뭉개거나 "대체로 잘 됐다"로 덮지 않는다 — **다운사이드를 인정하는 게 §8.2와 같은 기준**이다.
- **기록 위치 제안까지 한다:** 재발 방지가 필요하면 §3.2/§3.5에 규칙·*사례*로 추가한다(개인 메모리가 아니라 하네스 — §1).
- **승인 없이 만든 산출물은 목록으로 남긴다.** 유지/철회 판단이 안 났으면 `NOW.md`에 "처리 여부 미정"으로 명시해 다음 세션이 그걸 기정사실로 취급하지 않게 한다.

> *사례(2026-07-19, GAS Execution):* 세션 내내 규약을 안 따랐다는 사실이 **유저 질문("하네스 매번 확인하며 작업하는 거 맞아?")으로 드러났다.** 그 시점까지 decisions 3건 누락·worklog 0줄·타임스탬프 형식 위반이 쌓여 있었다. 회고가 절차에 없어서 스스로 점검할 지점이 없었던 것이 원인.

#### 3.3.2 하네스 자체 점검 — 규약이 틀렸거나 안 걸린 곳

**규약을 따랐는데도 문제가 생겼다면 규약이 부족한 것이다.** 세션 종료 시 아래를 확인하고, 해당하면 개정안을 유저에게 제안한다(문서를 임의로 고치지 않는다 — §3.2 "유저 의도를 넘어선 각색은 쓰기 전에 묻는다").

점검 항목:
- **트리거가 안 걸린 규칙이 있었나** — 조건이 좁아서 발동하지 않은 규약. (예: "구현 착수 전 HARNESS를 읽는다"가 *설명 → 논의 → 편집*으로 미끄러진 세션에선 한 번도 안 걸림 → CLAUDE.md 트리거를 "feature 관련 내용을 다루기 시작하면"으로 확장, 2026-07-19)
- **규칙끼리 충돌했나** — 어느 쪽이 우선인지 문서에 없어 임의 판단한 지점.
- **실제와 안 맞는 절차가 있었나** — 문서엔 있는데 현실적으로 수행 불가·불필요한 단계.
- **반복된 실수가 규약에 없나** — 같은 지적을 두 번 이상 받았으면 그건 개인 습관이 아니라 **빠진 규약**이다. §3.2/§3.5에 *사례*와 함께 추가를 제안한다.
- **기록 규약이 지켜졌나** — decisions 즉시 기록(§3.2)·`D#` 재번호 금지(§5)·타임스탬프 형식(§3.4)처럼 **놓치기 쉬운 형식 규칙**을 실제로 지켰는지 대조한다.

### 3.4 최종 갱신 타임스탬프 & 하류 문서 동기화 판별

**목적:** feature/구현이 바뀐 **날짜**를 기록해, 그를 요약·소개하는 하류 문서(`project/architecture/*`, `wiki/`)가 **무엇을 갱신해야 하는지 날짜 비교로 판별**할 수 있게 한다. (같은 날 안에서의 선후는 구분하지 않는다 — 그 정밀도가 필요한 적이 없었고, 시:분을 유지하는 비용이 더 크다.)

- **날짜 형식:** 모든 `최종 갱신`은 **`YYYY-MM-DD` (KST)** — **날짜만 적는다. 시:분은 쓰지 않는다.** 문서를 실제로 바꿀 때마다 그날 날짜로 갱신한다. (progress·feature-list·TODO-BOARD·architecture·wiki 공통)
- **날짜 출처:** 날짜는 **셸에서 확인**해 쓴다. 세션 컨텍스트가 제공하는 날짜를 그대로 신뢰하지 않는다(타임존·소스가 로컬과 다를 수 있다). 문서에 적기 전 한 번 확인한다.
  - **Claude Code 기준 — Bash 툴에서:** `TZ=Asia/Seoul date "+%Y-%m-%d"`
  - PowerShell 툴에는 `TZ=` 접두 문법이 없다. 그쪽을 쓸 거면 `(Get-Date).ToUniversalTime().AddHours(9).ToString("yyyy-MM-dd")`.
- **모르는 날짜는 지어내지 않는다 — 그 상태로 둔다.** 셸로 확인할 수 있는 건 "오늘"뿐이다. **과거에 무엇이 언제 반영·작성됐는지는 알 수 없으므로**, 낡은/빠진 타임스탬프(특히 하류의 `반영 기준`)를 그럴듯한 값으로 채우지 않는다 — 상류 progress의 날짜를 가져다 쓰는 것도 **추정이다**. 비어 있으면 **건드리지 말고 그대로 두고**, 필요하면 유저에게 보고만 한다. (틀린 값이 박히면 §3.4의 낡음 판별이 조용히 오작동한다 — 빈 값은 "모름"으로 드러나지만 가짜 값은 안 드러난다.)
  - *사례(2026-07-19):* `architecture/gameplay-effect.md`의 `반영 기준`에 상류 progress의 값을 가져다 채웠다. 그 문서가 실제로 그 시점 상태를 반영하는지는 확인할 방법이 없었다.
  - *사례(2026-07-19):* 세션 컨텍스트의 `2026-07-20`을 그대로 적어 7개 파일을 사후 정정했다. 로컬 KST는 `2026-07-19`였다.
- **상류 / 하류:** 진실의 출처는 **코드 + feature `progress.md`**(상류). 이를 요약하는 `architecture/*`·`wiki/`는 **하류**다.
- **하류의 반영 기준 마커:** 하류 문서(또는 wiki 섹션)는 상단/메타에 **`반영 기준: <상류 feature-id> @ <YYYY-MM-DD>`** 를 둔다 — "이 문서는 그 상류를 그 날짜 상태로 반영함"의 뜻.
- **갱신 필요 판별:** 하류의 `반영 기준` 날짜 < 상류 feature의 `최종 갱신` 날짜 이면 그 하류는 **낡음(갱신 후보)**. "무엇을 갱신할지"는 이 비교로 좁힌다.
  - `architecture/*`는 코드 변경과 **같은 세션 동기화가 원칙**(CLAUDE.md)이라 항상 최신이어야 한다.
  - `wiki/`는 `wiki/HARNESS.md` §0에 따라 **요청 시에만** 갱신하되, 이 비교를 낡음 리마인드의 근거로 쓴다.

### 3.5 대화 규율 (답변 방식)

**전제:** 유저와의 대화는 협업이지 발표가 아니다. 아래는 대인 커뮤니케이션 연구에서 "하면 안 되는 대화 방식"으로 정리된 것을 에이전트 상황에 옮긴 것이다. §3.2의 "대화 스코프를 벗어나지 않는다"가 이 절의 실천 지침이다.

#### 3.5.1 Grice 협력 원리 — 답변의 기본 격률

| 격률 | 요구 | 에이전트가 어기는 방식 |
|---|---|---|
| **양(Quantity)** | 필요한 만큼만. **요구된 것보다 더 많이 말하지 않는다** | 한 줄 질문에 다중 섹션 문서로 답변. 안 물어본 배경·대안·비교를 덧붙임 |
| **질(Quality)** | 근거 없는 걸 말하지 않는다 | 확인 안 한 API·동작을 단정 (CLAUDE.md "추측 금지"와 같은 규칙) |
| **관계(Relation)** | 관련된 것만 | 주제 밖 시스템·파킹 영역·이미 끝난 결정으로 새는 것 |
| **방식(Manner)** | 간결·명확·순서 있게 | 장황해서 정작 답이 묻힘. 결론을 뒤에 숨김 |

> 연구상 관계(Relation) 위반은 **회피·오도**로, 양(Quantity) 위반은 **과장·의도적 누락**으로 나타난다. 에이전트에겐 "질문은 좁은데 답이 넓어지는" 형태가 전형이다.

#### 3.5.2 하지 말 것 (Gordon의 커뮤니케이션 로드블록 중 해당분)

- **요청 없는 조언(Advising)** — "이렇게 하시죠"를 매 답변에 붙이지 않는다. 설명 요청엔 설명만.
- **훈계·강의(Teaching/Lecturing)** — 유저가 이미 아는 걸 다시 가르치지 않는다. 배경 설명은 유저가 모른다고 했을 때만.
- **과도한 되묻기(Questioning)** — 아래 §3.5.3.
- **화제 돌리기(Diverting)** — 답하기 애매한 지점에서 다른 주제로 옮겨가지 않는다. 모르면 모른다고 한다.
- **값싼 안심(Reassuring)** — "문제없습니다" 류로 넘기지 않는다. 근거 있는 평가만.
- **판단·비판(Judging)** — 유저 코드·결정을 결함 목록으로 나열하지 않는다. 지적은 **요청된 축**에서, 지목된 범위만.
- **내부 코드 풀어쓰기(Gloss)** — 유저에게 설명할 때 `D#`(decisions 결정 ID)·`S#`/`I#`/`E#`(로드맵 슬라이스)·`INV-#`(불변조건) 같은 **문서 내부 코드를 그대로 던지지 않는다.** 인용하는 순간 `<코드> — <한 줄 요지>` 형태로 푼다 — 유저는 그 코드를 외우고 있지 않아서, 코드만 쓰면 매번 문서를 열어야 하고 대화가 끊긴다. (문서 내부 상호참조 — worklog·decisions 간 — 는 코드만 써도 된다. 푸는 건 **유저에게 하는 설명**에서다.)
  - *사례(2026-08-04):* 답변에서 `D2`·`D5`를 설명 없이 인용해 "나는 그게 뭔지 모른다"는 지적을 받았다.

#### 3.5.3 질문에 질문으로 답하지 않는다

답을 알면서 되묻는 것은 **회피**이며, 반복되면 "물어도 직답이 안 온다"는 인식이 쌓여 신뢰를 깎는다. 또한 질문하는 쪽이 대화의 방향을 쥐므로 되묻기는 주도권을 가져오는 행위가 된다.

- **원칙: 먼저 답한다.** 되묻기는 답이 실제로 갈릴 때만, 그것도 **답을 준 뒤**에 붙인다.
  - ❌ "그건 어떤 용도로 쓰실 건가요?"
  - ✅ "지금 구조에선 A입니다. 다만 B 상황이면 달라지는데, 그 경우인가요?"
- 확인이 필요하면 **하나만**, 답이 바뀌는 지점만 묻는다. 여러 갈래를 한꺼번에 던져 유저에게 설계를 떠넘기지 않는다.
- 이미 유저가 답한 것을 다시 묻지 않는다(대화·문서에 답이 있으면 그걸 쓴다).

#### 3.5.4 주제를 유저에게서 뺏지 않는다 (shift ↔ support)

대화 연구에서 응답은 둘로 나뉜다 — **support response**(상대가 꺼낸 주제에 머무름)와 **shift response**(주의를 자기 쪽으로 옮김). 후자가 반복되면 대화가 탈선한다.

에이전트판 shift response:
- 유저 질문에 답하다 **자기가 발견한 문제**로 넘어가기
- 유저가 정한 작업 중에 **자기가 하고 싶은 리팩터·개선**을 끼워 넣기
- 유저의 좁은 질문을 **자기가 설명하기 좋은 넓은 주제**로 바꾸기

발견한 문제는 **기록하고(§7 TODO-BOARD) 한 줄로 보고**한 뒤 원래 주제로 돌아온다. 지금 답변의 주제를 바꾸지 않는다.

#### 3.5.5 자기 점검 (전송 전)

1. 유저가 물은 것에 **직접** 답했는가? 답이 첫 문단에 있는가?
2. 안 물어본 제안·비교·계획이 섞이지 않았는가?
3. 지금 주제 밖 시스템·결정을 꺼내지 않았는가?
4. 질문 한 줄에 답 열 줄로 대응하고 있지 않은가?
5. 내부 문서 코드(`D#`/`S#`/`INV-#` 등)를 인용했다면 한 줄 설명을 붙였는가?
6. 답변 끝에 **깔끔한 요약**(무엇을 했나·확인할 것)이 있는가? (§3.5.6 — 유저는 주로 요약만 읽는다)

#### 3.5.6 답변 끝에 항상 깔끔한 요약 (유저 지시, 2026-08-07)

**무언가를 수행했거나(작업·구현·변경) 여러 갈래로 설명한 답변은, 맨 끝을 깔끔한 요약으로 닫는다.** 유저는 본문 전체를 읽지 않고 **대부분 요약만 읽는 경우가 많다**(유저가 밝힘) — 요약이 사실상의 본문이라고 보고 쓴다.

- 요약에 담을 것: **무엇을 했나 / 결론** + (해당하면) **유저가 확인·할 일**. 스캔 가능하게 짧게.
- §3.5.1(양 격률: 본문은 짧게)과 충돌하지 않는다 — 요약은 본문을 늘리는 게 아니라, 긴 답변일수록 필요한 **착지점**이다. 본문이 길수록 요약은 필수.
- 답 자체가 한두 줄로 이미 짧으면 그게 곧 요약이므로 별도 섹션을 만들지 않는다(요약을 위한 요약 금지).

> 출처: Grice, *Logic and Conversation*(협력 원리·4격률) / Thomas Gordon, *12 Roadblocks to Communication* / Charles Derber, *The Pursuit of Attention*(conversational narcissism — shift·support response) / 질문 회피(deflection)의 신뢰 손상 효과.

## 4. feature-list.md 규약

`feature-list.md`는 프로젝트의 대시보드이며, 아래 형식을 따른다.

### 4.1 상태 정의

| 상태 | 의미 |
|---|---|
| `📋 PLANNED` | 등록만 됨. 설계/구현 미착수 |
| `🔧 IN-PROGRESS` | 현재 작업 중 |
| `⏸️ BLOCKED` | 블로커로 중단됨 (progress에 사유 필수) |
| `✅ DONE` | 완료. 수용 기준 충족 확인됨 |
| `🗄️ ARCHIVED` | 폐기 또는 통합됨 (사유 필수) |

### 4.2 상태 전이 규칙

```
PLANNED → IN-PROGRESS ⇄ DONE
              ↕
           BLOCKED
(모든 상태 → ARCHIVED 가능, 사유 필수)
```

- `DONE` 처리는 progress의 `## 수용 기준`이 전부 체크된 경우에만 허용한다.
- `DONE`인 feature를 다시 수정해야 하면 `IN-PROGRESS`로 되돌리고 사유를 기록한다.

### 4.3 목록 형식

그룹이 있으면 `###` 헤더로 묶고, 그룹 공유 하네스가 있으면 헤더 아래 링크한다. 그룹이 필요 없는 단일 feature는 헤더 없이 표 행으로 둔다.

```markdown
### 🧩 <group-id> — <그룹 이름>
공유 하네스: [HARNESS](feature/<group-id>/HARNESS.md)

| ID | Feature | 상태 | 우선순위 | 의존 | Progress |
|---|---|---|---|---|---|
| combat-core | 근접 전투 코어 | 🔧 IN-PROGRESS | P0 | - | [progress](feature/<group-id>/combat-core/progress.md) |
```

- 우선순위: `P0`(필수) / `P1`(중요) / `P2`(여유 시)
- `의존` 열에는 선행되어야 하는 feature-id를 적는다.
- 하위 feature ID는 그룹 안에서만 유일하면 된다(그룹이 네임스페이스). 표기는 짧게 `item`·`inventory`처럼.

## 5. progress.md 규약

각 progress 파일은 아래 템플릿 구조를 유지한다. **섹션을 임의로 삭제하지 않는다.**
**이 블록이 유일한 템플릿이다** — 별도 템플릿 파일을 두지 않는다(두 벌이 되면 갈라진다). 새 progress는 여기서 복사해 만든다.

```markdown
# <feature-id> — <Feature 이름>

- 상태: 🔧 IN-PROGRESS
- 우선순위: P0
- 최종 갱신: YYYY-MM-DD  (KST — §3.4)

## 목표
이 feature가 완성되면 무엇이 가능해지는가. (1~3문장)

## 수용 기준 (Definition of Done)
가능하면 **유저가 Unity 에디터에서 직접 확인 가능한** 조건으로 쓴다 (Play 모드 동작·Inspector 값·에디트 모드 동작 등). CLI 자동 테스트는 없다.
- [ ] 검증 가능한 조건 1
- [ ] 검증 가능한 조건 2

## 범위
### 포함
### 제외 (명시적으로 하지 않을 것)

## 설계 개요
핵심 구조, 관련 클래스/파일, 데이터 흐름 요약.

## 세부 TODO (구현 체크리스트)
이 feature를 완성하는 데 필요한 구현 작업을 순서대로 나열한다. 진행하며 ☑ 한다.
- [ ] 1. 작업 항목
- [ ] 2. 작업 항목

## 결정 기록
→ [decisions.md](decisions.md) (상세). progress엔 요지 인덱스만 (decisions.md와 같은 `D#` 공유).
| ID | 날짜 | 결정 (요지) |
|---|---|---|

## 작업 로그
→ [worklog.md](worklog.md) (시간순 이력은 별 파일). 재개 앵커는 아래 `## 다음 작업`.

## 블로커
(없으면 "없음"으로 명시)

## 다음 작업
1. 가장 먼저 할 일 (구체적으로: 파일, 클래스, 목표 단위)
2. 그 다음 할 일
```

### progress 작성 규칙

- **세부 TODO vs 수용 기준 vs 다음 작업** (혼동 금지):
  - `수용 기준` = 완료 판정(검증 가능한 **결과**). `세부 TODO` = 그 결과를 만들기 위한 **구현 작업 backlog**(과정). `다음 작업` = 세부 TODO 중 **다음 세션에 착수할 항목**을 구체 실행 지시로 지목.
  - 세부 TODO 항목을 끝내면 ☑ 하고, 필요하면 `다음 작업`이 그다음 미완 항목을 가리키게 갱신한다.
  - feature에 **전용 `HARNESS.md` 로드맵**(예: item의 S1~S10)이 있으면 그것이 세부 TODO 역할을 하므로, progress의 `## 세부 TODO`는 그 로드맵을 **가리키기만** 하고 중복 나열하지 않는다.
  - 이 세부 TODO는 feature 내부 작업용이다. feature와 무관한 잡다한 할 일은 여기가 아니라 `TODO-BOARD.md`(§7)에 둔다.
- **작업 로그는 feature 폴더의 `worklog.md`에 별도 보관**한다 (progress엔 `## 작업 로그` 헤더 + 포인터 링크만). 로그는 계속 자라는 아카이브라 매 세션 재로드 비용을 분리하려는 것 — 재개 앵커는 progress `## 다음 작업`이다. worklog는 **최신이 위로** 쌓는다.
- 로그는 "무엇을 왜 했는가" 중심으로 3~7줄 이내로 요약한다. 코드 전문을 붙여넣지 않는다.
- `결정 기록` **상세는 feature 폴더 `decisions.md`**에 둔다(§8 품질 기준: 맥락·대안·근거·결과·재평가 트리거). progress `## 결정 기록`엔 **요지 인덱스 + 링크만** (worklog와 같은 이유로 분리 — 해당 영역 건들 때 decisions.md 확인). 트레이드오프가 있었던 결정만, 사소한 네이밍 등은 제외.
- **`D#`은 유저가 확정한 결정에만 부여한다.** 에이전트가 스스로 내린 판단·제안 단계 결론을 D로 박지 않는다 — 결정 기록은 *유저의 판단*을 남기는 자리다. 제안 단계에서는 `worklog.md`·progress에 **"제안"으로 적고**, 유저가 확정한 뒤에 D를 부여한다. (판단 근거·대안 정리는 제안 단계에서 해도 되지만, 그게 곧 결정은 아니다.)
  - *사례(2026-07-19):* 에이전트가 "AttributeCapture 미도입"을 자기 판단으로 `D6`까지 붙여 확정했으나, 유저 방향은 **도입**이어서 폐기·결번 처리됐다. 그 사이 5개 문서가 D6을 근거로 인용해 전부 정정해야 했다.
- **식별 코드:** 각 결정엔 feature 내 고유한 `D1`·`D2`…(순번, 재번호·재사용 금지)를 부여한다. decisions.md와 progress 인덱스가 같은 ID를 공유하고, worklog·`다음 작업`에서 결정을 가리킬 땐 `(→D3)`처럼 코드로 링크한다. 로드맵 슬라이스(`S#`/`I#`/`E#` 등)도 worklog에서 같은 방식으로 참조해 **"언제(worklog) → 무슨 작업(S/I/E) → 왜(D)"**가 코드로 이어지게 한다.
- **`최종 갱신`은 날짜만**(`YYYY-MM-DD`, KST — 시:분 없음) 적고, 문서를 바꿀 때마다 그날 날짜로 갱신한다 — 하류 문서(architecture·wiki) 동기화 판별의 기준(§3.4).
- `다음 작업`은 항상 **실행 가능한 수준**으로 구체화한다.
  - 나쁜 예: "전투 시스템 개선"
  - 좋은 예: "`AttackState.cs`에 콤보 입력 버퍼(0.3s) 추가 후 `PlayerStateMachine` 전이 연결"

## 6. Feature 생성 / 완료 / 폐기 절차

### 신규 feature 등록
1. `feature-list.md`에 행 추가 (`📋 PLANNED`)
2. `feature/<feature-id>/` 폴더를 만들고, §5의 템플릿을 복사해 `progress.md` 생성 (구현 방향·불변 조건·로드맵이 방대하면 같은 폴더에 `HARNESS.md`도 작성)
3. `목표`, `수용 기준`, `범위`를 반드시 채운 후 작업 착수

### 완료 처리
1. `수용 기준` 전 항목 체크 확인
2. progress 상태 → `✅ DONE`, 최종 로그 기록
3. `feature-list.md` 상태 동기화
4. **wiki 갱신 리마인드(마일스톤):** feature를 `✅ DONE` 처리했으면, 포트폴리오 wiki(`wiki/`)가 낡았을 수 있음을 유저에게 **한 줄 리마인드**한다. — wiki를 직접 고치지는 않는다(갱신은 요청 시에만; `wiki/HARNESS.md` §0). 어긋날 만한 섹션이 짐작되면 함께 짚어준다. (예: "item-system 완료 — wiki의 `arch`/`todo` 섹션이 코드와 어긋날 수 있으니 갱신할까요?")

### 폐기/통합 처리
1. progress 최상단에 폐기 사유 및 (통합 시) 대상 feature-id 기록
2. 양쪽 문서 상태를 `🗄️ ARCHIVED`로 동기화

## 7. 작업 보드 (TODO-BOARD.md)

`feature-list.md`가 **feature 단위**를 추적하는 반면, `TODO-BOARD.md`는 그보다 **잘게 쪼개진 잡다한 작업·개인 TODO·이슈**를 모으는 별개 레이어다. (문서 정비, 인프라, 실험, 리팩터, 아이디어 등 feature로 묶기 애매한 것)

### 7.1 구조
- 상태 3칸 고정: `## 📋 TODO` → `## 🔧 진행 중` → `## ✅ Done`. 항목은 상태가 바뀌면 해당 칸으로 **이동**한다(복제 금지).
- **단, 이 3칸은 에이전트가 지키는 기본 틀일 뿐이다 — 보드는 유저도 직접 쓴다.** 유저가 칸을 쪼개 두었거나(예: `📋 TODO (당장 목표)` / `📋 TODO (우선순위 낮음)`) 형식에서 벗어난 항목이 있으면 **그대로 존중하고, 규약에 맞춘다며 임의로 재편·병합·삭제하지 않는다.** 에이전트는 기존 구조에 얹어서 쓰고, 구조 변경이 필요해 보이면 제안만 한다.
- 항목 형식: `- [ ] **(범주)** 내용 — 비고 _(YYYY-MM-DD 등록)_`. 완료 시 `- [x]` + 완료일. 범주 예: `wiki`·`docs`·`infra`·`bug`·`idea`.
- 각 칸이 비면 `(없음)`으로 명시한다.

### 7.2 유지 규약 (반자동 — 훅 아님)
- **세션 시작 시** 이 보드를 한 번 훑는다(`진행 중`에 걸린 게 있는지 확인).
- **포착:** 채팅·작업 중 할 일/이슈/아이디어가 나왔는데 보드에 없으면 → 그 자리에서 `📋 TODO`에 추가한다. (사용자가 명시적으로 지시하지 않아도, 놓치지 않게 잡아 둔다)
- **상태 전이:** 어떤 항목에 착수하면 `🔧 진행 중`으로, 끝나면 `✅ Done`(완료일 기입)으로 옮긴다.
- feature 단위로 커진 항목은 보드에서 빼고 `feature-list.md`에 등록한다(중복 추적 금지).
- 상단 `최종 갱신` 날짜를 바꿀 때마다 갱신한다.

## 8. 포트폴리오·면접 대비 (산출물 기준)

평가 대상은 **코드의 양이 아니라 판단의 질 + 굴러가는 데모**다. 면접·포트폴리오가 실제로 검증하는 건 "무엇을 만들었나"보다 **"왜 그렇게 결정했고, 어떤 대안을 두고 무엇을 포기했나"**이므로, 모든 작업은 아래를 산출물로 남긴다. (판단이 문서화 안 된 코드는 산출물로 인정하지 않는다 — §1)

### 8.1 결정 기록 품질 기준

트레이드오프가 있는 결정은 feature 폴더 `decisions.md`에 아래를 담아 **상세히** 남긴다 (progress `## 결정 기록`엔 요지 인덱스 + 링크만 — §5). 표 `채택 사유` 칸에 서술로 압축, INV 관련 결정은 근거에 INV-ID 명시. (자명한 선택·네이밍은 제외 — 과잉 기록은 유지 부담)

- **맥락(forces):** 왜 이 결정이 필요했나 — 충돌한 제약·요구.
- **대안:** 진지하게 검토한 후보 + 각 장단 (버린 것도 이유와 함께).
- **근거:** 왜 이걸 택했나, 그리고 **왜 대안이 아니었나**.
- **결과·트레이드오프:** 무엇을 얻고 **무엇을 포기했나** — 부정적 결과를 반드시 포함.
- **재평가 트리거:** 이 결정을 뒤집을 조건 (예: item의 "복수 부위 점유 시 `SlotType[]` 확장").

### 8.2 "왜"의 품질 — 기술 주장이 아니라 결과·맥락에 연결

면접에서 트레이드오프 서술은 시니어급일수록 가장 무겁게 채점된다. 다운사이드를 인정하는 게 성숙함의 신호이고, 단점 없는 선택처럼 쓰면 판단을 안 한 것으로 읽힌다.

- ❌ 약함: "캐시가 더 빠르니까" (맥락 없는 기술 진술)
- ✅ 강함: "읽기 지연은 줄지만 최종 일관성을 감수 — 이 기능은 신선도보다 속도가 중요해 허용"
- 기준: **한 결정을 한 문장으로 "왜"까지 말할 수 있어야 한다** (CLAUDE.md 개발 방향). 말이 막히면 근거가 부족한 것.

### 8.3 데모·서사

- **굴러가는 데모:** 슬라이스는 완료 시 에디터에서 눈으로 확인 가능해야 한다 (수직 슬라이스; feature 로드맵이 있으면 그것). "아름다운 설계"가 아니라 **"굴러간다 + 왜 이렇게 했는지 설명된다"**가 완성.
- **서사:** `worklog.md`는 시간순 "판단의 이야기"로 읽히게 쓴다 — 무엇을 왜 했고, 어디서 막혀 어떻게 풀었나. 리뷰는 과정 나열이 아니라 스토리를 본다.
- **절제도 산출물:** 과설계는 감점이다. "필요 없지만 인상적이라 추가" 금지, 절제한 판단(왜 단순한 쪽을 택했나)도 기록 대상이다 (북극성).

### 8.4 "왜"는 지어내지 않는다 — 유저가 말한 것만 적는다

§8.2가 "왜"를 요구한다고 해서 **에이전트가 근거를 만들어 채우라는 뜻이 아니다.** 근거·배경·채택 이유는 **유저가 실제로 말한 것만** 문서에 적는다.

유저가 결론(무엇을)만 말하고 근거(왜)를 말하지 않은 경우:

1. 유저가 말한 **결론만** 적는다.
2. 근거 자리는 **비워 두고**, 비어 있다는 사실을 문서에 명시한다 — 예: `> 이 결정의 근거는 아직 기록되지 않았다(유저 확정 전).`
3. 같은 턴에 **유저에게 근거를 묻는다.** 답을 받으면 그때 채운다.

그럴듯한 근거를 대신 써 두면 유저 본인의 판단으로 굳어져 나중에 구분할 수 없게 된다. 포트폴리오 문서에서 이건 **없는 것보다 나쁘다** — 면접에서 본인이 설명 못 하는 근거가 문서에 남는다.

이 규칙은 `decisions.md`의 `D#`뿐 아니라 **architecture·progress·worklog 등 모든 문서의 서술**에 적용된다. 코드 사실(무엇이 어떻게 동작하는지)은 읽어서 확인한 대로 적어도 되지만, **"왜 그렇게 했는가"는 확인 없이 쓰지 않는다.**

> 2026-07-20 실제 발생 — ability-system overview에 유저가 말한 설계 목적 한 줄을 받아, 에이전트가 채택 이유 3건과 적용 예를 추론해 덧붙였다. 되돌리고 이 규칙을 신설.

### 8.5 "왜"의 근거는 유저 의도 → UE 원본 순 — 코드 동작은 근거가 아니다

"이 설계가 왜 이런가"를 설명할 때, **코드가 그렇게 동작한다는 서술을 근거로 들지 않는다.** "이 함수가 리스트를 Clear하니까 별도 리스트가 필요하다"류는 *무엇이 일어나는지*일 뿐 *왜 그렇게 설계했는지*가 아니다 — 코드로 코드를 정당화하는 순환이라 근거로서 무의미하다(유저 표현: "코드 근거는 진짜 의미 없다").

근거의 순서:

1. **유저의 실제 의도가 최상위 근거.** 이 프로젝트는 UE GAS를 **참고**하지만 **단순 복제가 목표가 아니다** — 설계를 지배하는 건 유저의 의도다. 그러니 "왜 이런가"의 최종 근거는 유저가 실제로 무슨 의도였는지이며, 이건 **지어내지 않고 유저에게 묻는다**(§8.4와 같은 뿌리). 확인 전까진 근거 자리를 비워 둔다.
2. **그다음이 UE 원본.** UE는 "성숙한 설계는 이 문제를 어떻게 푸나"의 강한 참조·근거다. 유저 의도가 아직 없거나 의도를 UE와 대조해 정할 때 쓴다. 단 **기억으로 단정하지 말고 원문을 확인하고**(§1.1 — ylyking UE 미러·Epic 문서), **UE와 갈리는 지점(divergence)은 결함이 아니라 의도된 선택일 수 있다** — "UE라서"로 유저 의도를 덮지 않는다.

> 2026-08-03 실제 발생 — "캡처 컨테이너가 definitions를 spec과 따로 둔 이유"를 코드 동작(`CaptureAttributes`가 Clear·재캡처)으로 설명했다. 코드 근거는 방향 자체가 틀렸다. UE 원문 확인은 "UE는 안 나눈다"는 **참조**를 줬지만, 실제로 그 divergence를 없앨지는 **유저가 결정**했다(유지할 수도 있었음) — 최종 근거는 유저 의도, UE는 그 판단을 뒷받침한 참조.
