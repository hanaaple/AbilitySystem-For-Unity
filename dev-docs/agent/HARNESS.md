# HARNESS.md — Agent 작업 규약

## 에이전트 핵심 원칙

1. **문서가 곧 상태(State)다 — 문서에 없는 작업은 없었던 작업이다.**
   - **작업 규약·소통 방식·재발 방지 지침("앞으로 이렇게 해라"류)은 개인 메모리가 아니라 하네스(또는 `dev-docs/`)에 적는다.**
2. **읽기 → 작업 → 기록. 기록 없이 세션을 종료하지 않는다.**
   - **의미 있는 진전(결정·구현·에셋)마다 즉시, 시키지 않아도 기록한다.** 몰아서 하지 않는다.
   - 우선순위: 진전마다 **`NOW.md`** 먼저, 결정이면 `decisions.md`, 구현이면 `worklog.md`/progress. 한 턴이 커지면 중간에도 남긴다.
   - 확실한 종료 리마인드는 **Stop 훅**(요청 시).
3. **하나의 세션, 하나의 feature.** 다른 feature의 코드를 수정해야 하면 그 feature progress에 사유를 남긴다.
4. **추측 금지.** progress와 실제 코드가 다르면 코드를 진실로 보고 progress를 고친 뒤 시작한다.
   - `NOW.md`·progress·worklog를 현재 상태로 단정하지 말고, "지금 어떠하다" 말하기 전에 **실물(코드·에셋·git)을 확인**한다.
5. **판단은 틀릴 수 있다 — 자기 출력을 항상 "틀렸을 수 있는 것"으로 다루고 근거와 확신도를 드러낸다.**
   - **주장과 근거를 분리한다.** "X다"가 아니라 "**무엇을 보고** X라 판단했는지"(읽은 파일·줄, 실행 명령, 검색 출처)를 같이 낸다.
   - **확신도를 구분한다.** **직접 읽은 코드**(확정)와 **외부 API·엔진 동작 기억·2차 자료**(불확실)를 같은 어조로 말하지 않는다.
     - **트리거:** 엔진·외부 API 동작 질문("UE는 어떻게 하나" 류)엔 답을 쓰기 전에 멈추고 **원문부터** 확인한다 — 기억·2차 자료(포럼·블로그·WebFetch 요약)로 먼저 답하지 않는다. 결론이 걸린 지점은 원문 라인을 직접 본다.
   - **모르면 모른다고 한다.** GUID·경로·버전·날짜 등 값·식별자는 **조회해서** 쓴다 — 지어내지 않는다.
   - **반박당하면 방어부터 하지 않는다.** 유저가 다른 정보를 주면 **내 근거 강도부터 다시 본다.**
   - **한 번 틀린 종류는 기록한다**(session-protocol '하네스 자체 점검').
6. **해석 규율 — 일반화·섣부른 판단 금지. 관측 범위를 넘어 결론을 넓히지 않는다.**
   - **사례 1건을 일반 규칙으로 만들지 않는다** · **중의적 문장을 한 해석으로 굳히지 않는다**(두 갈래면 그렇게 말하고 가릴 방법 제시) · **부분 관측을 전체로 확대하지 않는다**(확인한 경로 명시).
   - **이름·용어가 같아도 계층·의미가 다를 수 있다**(예: Unity `CharacterController` ≠ UE `CharacterMovementComponent`).
   - **추론은 추론이라 표시하고 확인 가능하면 확인한다.**
   - **유저 목표를 확인하기 전엔 "필요/불필요"를 세게 단정하지 않는다.** "과설계니 하지 말자"류 가치판단은 유저 의도(1순위)를 먼저 확인한 뒤 — 트레이드오프 제시까지만, 결론은 미리 못박지 않는다.
   - 자문: **"내가 실제로 본 것은 어디까지이고, 어디부터가 내 추론인가?"**
7. **읽기 트리거가 거부·중단돼도 규약을 끄지 않는다.**
   - **원칙은 메모리로 유지한다.** 문서를 안 열었어도 5·6·8번은 계속 적용한다.
   - **첫 재시도 지점:** ① `dev-docs/` 문서를 쓰거나 고치기 직전, ② 되돌리기 비용 있는 구조 결정(데이터 모델·레이어 신설 등) 직전.
   - 세션 내내 규약이 안 켜졌으면 그 사실을 session-protocol '세션 회고'에 남긴다.
8. **"왜"는 지어내지 않는다 — 유저가 말한 것만 적는다.** 근거·배경·채택 이유는 **유저가 실제로 말한 것만** 적는다.
   - 유저가 결론만 말하고 근거를 안 말했으면: ① 결론만 적고 ② 근거 자리는 비워 두되 비었음을 명시(`> 근거 미기록(유저 확정 전)`) ③ 같은 턴에 유저에게 묻는다.
   - `decisions.md`뿐 아니라 architecture·progress·worklog 모든 서술에 적용(코드 사실은 확인한 대로 적어도, "왜"는 확인 없이 쓰지 않는다).

## 프로젝트 핵심 원칙

1. **목적은 포트폴리오 — 평가 대상은 판단의 질 + 굴러가는 데모.**

   설계 결정에는 기술적 근거와 선택 이유가 드러나야 하고, **판단이 문서화 안 된 코드는 산출물로 인정하지 않는다.**

2. **과설계 금지 — 완성도 집착으로 게임 완성을 저해하지 않는다.**

   "필요 없지만 인상적이라 추가" 금지, **절제한 판단(왜 단순한 쪽을 택했나)도 기록 대상이다.**

3. **"왜"는 결과·맥락에 연결한다 — 맥락 없는 기술 진술 금지.**

   트레이드오프는 다운사이드까지 인정해 서술한다(❌ "캐시가 빠르니까" / ✅ "읽기 지연은 줄지만 최종 일관성 감수 — 속도가 중요해 허용"). **한 결정을 한 문장으로 "왜"까지 말할 수 있어야 한다**(막히면 근거 부족).

4. **"왜"의 근거는 유저 의도 → UE 원본 순 — 코드 동작은 근거가 아니다.**

   ① 유저 의도가 최상위(지어내지 말고 유저에게 묻고, 확인 전엔 비워 둠 — 에이전트 원칙 8), ② 그다음 UE 원본(기억 말고 원문 확인, divergence는 의도된 선택일 수 있음). **"UE를 따른다"=본질·방향성이지 세부 구현 복제가 아니다** — UE 고유 제약(네트워크 복제·legacy)에서 온 구현은 그 제약이 없으면 따르지 않고, **"UE가 왜 이렇게 했는지 → 우리에게도 성립하는지"**를 먼저 판단한다.

5. **굴러가는 데모 = 완성.**

   슬라이스는 완료 시 에디터에서 눈으로 확인 가능해야 하고(수직 슬라이스), **`worklog.md`는 시간순 "판단의 이야기"로 쓴다** — 무엇을 왜 했고, 어디서 막혀 어떻게 풀었나.

> **결정 기록(decisions.md)의 상세 품질 기준**은 `feature/HARNESS.md`('결정 기록 품질 기준')에 있다.

## 관련 하위 문서 및 폴더 (Indexing)

- `HARNESS.md` — 그 폴더·하위 폴더에 적용되는 **공통 규약 문서**(폴더마다 있을 수 있고, 경로 위의 것을 모두 적용).
- **하위 폴더는 그 폴더의 `HARNESS.md`에 위임한다** — 내부 파일을 여기서 나열·설명하지 않는다.

**폴더**

| 폴더 | 내용 |
|---|---|
| `feature/` | feature 문서 규약 허브 → [feature/HARNESS.md](feature/HARNESS.md) |

**규약 문서** (agent/)

| 문서 | 내용 |
|---|---|
| `session-protocol.md` | 세션 시작·작업 중·종료·타임스탬프·대화 규율 |
| `todo-board-convention.md` | `TODO-BOARD.md` 규약 |

**agent 상태 문서**

| 문서 | 내용 |
|---|---|
| `NOW.md` | 단일 재개 지점 — 휘발성 재개 메모(진실의 출처 아님). 지금 할 일·멈춘 지점·선행조건만 짧게. **개인용 로컬 파일**(`.gitignore`, 미커밋) — 각 작업 환경이 자기 것을 생성·유지하며, 없으면 이어하기 시 새로 만든다. 팀 공유 상태는 progress·decisions·feature-list. |
| `TODO-BOARD.md` | 잡다한 작업·이슈 보드 |
