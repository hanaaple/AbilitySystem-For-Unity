## 1. 프로젝트 방향성 (유지)

- **목적:** 게임 클라이언트 프로그래머 포트폴리오. 산출물의 크기가 아니라 **판단의 질과 굴러가는 데모**가 평가 대상.
- **북극성:** "필요해지는 트리거가 오기 전엔 더 복잡하게 만들지 않는다." 모든 구현 판단에서 단순한 쪽이 디폴트.
- **과설계 경계:** 규약·패턴·추상화는 그 자체가 목적이 아니다. "이걸 왜 쓰는지 한 문장으로 설명 가능한가"가 통과 기준. 설명이 "규약이 그러라고 해서"면 그 규약을 의심한다.
- **스코프:** 탑다운 추출(extraction-lite) + 빙의 컨셉의 싱글플레이. 무기는 **총·검·특이 무기를 대등하게** 다룬다 — 무기 종류마다 배타적인 주 행동 알고리즘이 계속 늘어나므로 **"무기 추가 시 중앙 시스템 무수정, 자기 완결적으로 붙는 확장성"이 1순위 요구**다. 등급/네트워크/세이브는 범위 밖 — 요청받지 않는 한 그 방향의 코드·필드·주석을 만들지 않는다.
- **완성의 정의:** "설계가 아름답다"가 아니라 **"수직 슬라이스가 실제로 굴러간다 + 왜 이렇게 했는지 문서로 설명된다"**.

## 2. 아이템/무기 구조 (결정 — 2026-07-18)

### 판단 기준 (근거)
2026-07-10~12 설계 재검토에서 채택한, Nystrom *Game Programming Patterns*(Type Object vs Subclass Sandbox) 기반 판단 축. 아래 결정의 근거다.

1. **변하는 것이 데이터인가, 알고리즘인가** — 데이터면 에셋+필드(조합), 알고리즘이면 코드(얕은 서브클래스).
2. **두 축이 직교해 곱해지나, 배타적인가** — 곱해지면(불붙은 검/총) 조합, 배타적이면(검이면서 총일 수 없음) 서브클래스.
3. **누가·언제 확장하나** — 비프로그래머·런타임 확장이 없으면 "코드 0줄 조합"의 기술적 동기는 약하다(시연 가치와 구분).
4. **결합을 어디에 모으나** — 파생이 외부 시스템을 알아야 하면 베이스가 파사드로 툴박스(제공 연산)를 내어주고, 비대해지면 헬퍼로 위임.

### 결정: 안 A — 무기 Base(추상) + 무기별 서브클래스, 구체 무기는 데이터
- **무기 종류 = 코드 타입.** `WeaponBase`(추상)가 공통 뼈대를 잡고, 씬 접근은 **제공 연산(툴박스, Subclass Sandbox)**으로 내어준다. 무기별 서브클래스(Sword/Gun/…)가 **주 행동 알고리즘(축 A)** 과 **per-instance 상태·tick(축 D: 탄약·재장전·콤보 등)** 를 구현한다.
- **구체 무기(특정 검·특정 총)는 서브클래스가 아니라 에셋 데이터(파라미터, 축 B)** 로 찍어낸다. → 무기 *종류* 추가 = 코드, 무기 *종* 추가 = 데이터.
- **시스템(장비/전투)은 `weapon.Attack()` 한 줄 — 무기 종류 분기 없음.** → "무기 추가 시 중앙 시스템 무수정, 자기 완결적으로 붙는다"는 스코프 1순위 요구 충족.
- 근거: 무기 다양성(총·검·특이)으로 축 A가 계속 늘어남 → 안 B(시스템이 알고리즘 보유)는 무기마다 중앙 분기가 쌓여 탈락. 안 C(어빌리티 확장)는 지금 없는 어빌리티 시스템 신설 비용으로 보류. 상세 → [item/decisions.md](item/decisions.md).

### Module 레이어 = 보류
- 축 C(직교 부가효과: 이속 −5, 온히트 화상 등)의 **Module 시스템은 이번 설계에서 뺀다.** 지금 필요 트리거가 없다(북극성). 필요해지면 그때 `WeaponBase`의 훅(OnEquip/OnHit 등)으로 재도입.
- 따라서 기존 코드의 `~Module`·`WeaponAttackComponent`·`ModuleContext`·`Strategy/`는 이 결정에 따라 **정리 대상** — 단, 코드 리팩터는 별건이며 아직 미착수(문서 확정이 먼저).

### 구조 스케치
```
ItemAsset (SO, 무상태 템플릿)
  └ WeaponAsset : ItemAsset          // 어느 Runtime 타입인지 + 파라미터(축 B)
       SwordAsset { range, damageGE, ... }
       GunAsset   { range, damageGE, magazine, fireRate, ... }

WeaponBase (추상 런타임 = per-instance 상태 소유 + 제공 연산 파사드)
  ├ protected OverlapForward(r) / RaycastForward(r) / ApplyEffect(target, ge)   // 툴박스
  ├ abstract Attack();   virtual Tick(dt);
  ├── SwordWeapon { int _combo; float _window;  Attack(){...} }   // 축 A + D
  └── GunWeapon   { int _ammo;  float _reload;   Attack(){...} }   // 축 A + D
```
> 씬 접근에 필요한 최소 컨텍스트(소유자 ASC + Transform 등)는 장착 시 **다운캐스트 없는 구체 타입 하나**로 주입 (과거 `AbilitySystemModuleContext` 다운캐스트 문제 재발 방지). 팀/적대 판별 형태는 [item/decisions.md] 후속 미결.

> ⚠ 구조는 확정. 단 **코드 착수 전** 남은 미결(컨텍스트 최소 집합, tick 주체 = 장비 컴포넌트 vs 얇은 전투 드라이버)은 구현 시점에 결정. 현황은 `dev-docs/agent/NOW.md`.

## 3. 문서 갱신 규약 (유지)

- 세션/작업이 끝날 때 인계는 별도 파일 없이 세 곳에 반영: **worklog.md**(무엇을 왜 했나) · **progress `## 다음 작업`**(다음 사람이 첫 30분에 할 일) · **decisions.md**(내린 판단과 근거).
- 판단이 문서화 안 된 코드는 인계로 인정하지 않는다 — 코드와 "왜"가 세트다(포트폴리오 목적상 판단 기록 자체가 산출물).
- 설계 문서를 임의 수정하지 않는다. 설계 변경이 필요하면 제안하고 유저 승인 후 반영.
