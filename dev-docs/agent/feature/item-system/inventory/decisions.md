# inventory — 결정 기록

> 트레이드오프가 있었던 설계 결정의 상세(맥락·대안·근거·결과·재평가 트리거). 품질 기준은 일반 [HARNESS.md](../../../HARNESS.md) §8.
> **ID(`D#`)는 feature 내 고유·불변**이며 progress 인덱스·worklog가 이 코드로 이 표를 가리킨다. progress엔 요지 인덱스만 두고, **해당 영역을 건들 때 이 파일을 연다.**

| ID | 날짜 | 결정 | 대안 | 채택 사유 |
|---|---|---|---|---|
| D1 | 2026-07-05 | 원래 `item-system` feature를 `item`/`inventory-system`/`equipment-system`으로 **3분할**. 이 feature는 인벤토리만 | 단일 feature 유지 | 아이템 코어·인벤·장비는 수명·의존이 다른 관심사. 분리해야 각자 스코프·검증이 선명. equipment는 현재 제외 |
| D2 | 2026-07-05 | **인벤 스코프에 개수·스택 포함** (§1의 "개수 제외"를 인벤 도메인에 한해 확장). 세이브·네트워크는 계속 제외 | 1아이템 1엔트리(개수 제외) | 유저 결정. 포션 등 수량 아이템이 실사용에 필요. 단 확장은 개수/스택까지고, 영속화(세이브)는 여전히 스코프 밖으로 경계 유지 |
| D3 | 2026-07-05 | 인벤은 **무의존 순수 컨테이너**, `CharacterBase`가 소유, 소비처(UI)는 이벤트 구독. ASC/`PlayerCharacter` 참조 안 함 | 인벤이 캐릭터/장비를 직접 참조 | "연결되지만 종속 안 됨" 요구. 컨테이너가 액터를 모르면 적·상자에도 재사용 가능하고 씬 없이 테스트됨(INV-6/7/8) |
| D4 | 2026-07-05 | **엔트리·스택 모델**: `InventoryEntry{ItemData Data; int Count; ItemInstance Instance}`. 스택은 **능력 인터페이스** `IStackable{ int MaxStack }`로 표현 — 스택되는 종류만(소비·미래 충전형) 구현, **장비는 미구현→스택 불가**. `IStackable`=`(Data,Count)` 병합·`Instance=null`, 비스택(장비)=엔트리별 고유 `ItemInstance`·Count=1 | ① 전 아이템 공통 `ItemData.MaxStack`(기본 1) 필드 ② 카테고리 하드코딩(EquipItem→1) ③ 소비도 유닛마다 `ItemInstance` | 유저 지적("장비엔 스택 개념이 없다")대로 **스택은 일부 종류의 능력**이지 전 아이템 속성이 아님 → 공통 필드는 장비에 무의미. `IEquippable`과 동형의 능력 인터페이스로 두면 장비엔 필드가 안 붙고 컨테이너는 `is IStackable`로 판별(INV-11). 장비는 per-item 모듈 상태(`ItemInstance`)를 가져 병합 시 오염되므로 개별 엔트리 필수. 소비는 무상태라 count로 충분(99개 인스턴스 낭비 회피). **트레이드오프:** `IStackable`+`ConsumeItem.MaxStack`가 item 코어(교차 feature)에 침투. **재평가 트리거:** 장비/충전형에 스택·충전 상태가 필요해지면(예: 소모성 투척 장비, 충전량 보존) `ItemInstance` 소유·스택 정책 재검토 |
| D5 | 2026-07-05 | 장비/소비 **저장은 단일 컬렉션**, 종류 구분은 `ItemData` 타입·능력(`is IEquippable`/`is IStackable` 등)에서 파생하는 **읽기 질의**로 노출 | 종류별 분리 컬렉션(장비함/소비함) | 유저의 "장비/소비로 나뉜다"는 **분류/조회** 요구지 저장 이원화 요구가 아님. 게다가 유저가 "필터가 더 다양해질 것(충전형 등)"이라 밝힘 → 저장을 종류로 이원화하면 종류가 늘 때마다 컬렉션이 늘어 확장에 취약. 단일 컬렉션 + 술어 질의면 **새 종류는 질의만 추가**하면 되고 추가/제거/스택 로직은 한 벌, 컨테이너가 카테고리를 몰라도 됨(INV-7/11). **트레이드오프:** 종류별 **용량 상한**(장비칸 N개 등) 요구가 오면 그때 분리/파티션 필요 — **재평가 트리거** |
| D6 | 2026-07-05 | 인벤 **수명 = 소유자 수명**. 세이브 없음 → 캐릭터 파괴 시 자연 소실, 사후 잔존(빙의 전환) 시 `OnDeath` 구독해 `Clear()`. 드롭·시체 루팅·이전은 스코프 밖 | 사망 시 아이템을 월드에 드롭/이전 | 유저의 "죽으면 모든 아이템 상실"(로그라이크 permadeath) 요구를 가장 단순히 충족. 소유가 `CharacterBase`라 수명이 자연히 귀속됨. **재평가 트리거:** 시체 루팅·사망 드롭 기획이 생기면 소실 대신 드롭 경로 추가 |
| D7 | 2026-07-05 | **UI 이번 범위 제외**(유저 지시). `OnChanged` 등 이벤트는 코어에 노출하되 구독 UI(I3)는 보류 | UI까지 이번에 구현 | 유저가 "UI 연동은 빼두고" 명시. 이벤트를 미리 노출해 두면 나중 UI가 폴링 없이 붙음(INV-8). 코어·컴포넌트 검증에 UI는 불필요(EditMode 테스트로 대체). **트레이드오프:** 눈으로 보는 데모는 테스트/로그로 대체 |
| D8 | 2026-07-05 | **Inventory 소유를 GameObject/씬에 묶지 않는다.** `Inventory`/`InventoryEntry`는 **소유자 미지정 POCO**. 장기 보유는 지속 소유자 계층(현재 미존재)이 생기면 그가 생성·보유하고, 씬 `InventoryComponent`는 소유가 아니라 그 POCO를 **바인딩하는 뷰**. "사망 소실"은 소유자가 `Clear()`를 구동(GameObject 파괴가 아님). **D3의 "CharacterBase 소유" 프레이밍을 대체하고 D6를 정제** | (a) 인벤을 캐릭터 GameObject 컴포넌트가 소유 (b) 전역 단일 인벤 | 유저 요구: "단순히 몸체에 종속돼 씬/종료와 함께 사라지면 안 됨" + "타 캐릭터도 각자 인벤". (a)는 씬 언로드·몸체 재생성에 데이터가 함께 죽어 요구 위반. (b)는 per-character 위반. `Inventory`가 POCO라 씬 수명과 무관(참조가 살면 산다)한 점을 이용해 **소유를 중립으로** 두면 둘 다 충족되고, item 시스템의 데이터(POCO)/표현(MonoBehaviour) 분리와 동형. **결과·트레이드오프:** I1(순수 코어)은 무블로킹으로 지금 구현 가능하나, 지속 소유자가 없어 **I2(컴포넌트·사망 배선)는 보류**. **재평가 트리거:** 지속 캐릭터 데이터/런 컨텍스트 계층이 등장하면 그것을 소유자로 배선 |
