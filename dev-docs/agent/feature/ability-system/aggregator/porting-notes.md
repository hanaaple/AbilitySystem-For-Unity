# aggregator — GAS 포팅 리서치 노트 (임시)

> **성격:** 유저가 UE GAS 의존성 전파를 리서치하며 정리한 **임시 뭉텅이 노트**다(2026-08-15 인계).
> **미검증·미완:** 코드·문서·유저 이해 모두 진행 중. 진실의 출처가 아니다 — 확정 설계는 [decisions.md](decisions.md), UE 원문 정리는 [ue-reference.md](ue-reference.md).
> 이 문서는 정리·각색 없이 그대로 스태시한 것이며, 이후 검증/확정되면 해당 항목을 decisions·architecture로 승격한다.

## Q1. 왜 OnDirty 하나로 옵저버 패턴만 쓰지 않고 Dependents를 따로 뒀나?

질문 배경: 값 바뀌면 알리는 델리게이트 하나면 충분해 보임.

결론: 방향이 반대인 두 가지 요구.

- **OnDirty** = "내 값 바뀜, 화면에 반영해" (출력)
- **Dependents** = "너 나 쓰지? 다시 계산해" (입력)

OnDirty만 있으면 광전사 버프(공격력 += 잃은 체력 × 0.1)에서 체력이 변해도 공격력을 아무도 다시 계산해주지 않음. OnDirty는 자기를 입력으로 쓰는 게 누군지 모름.

## Q2. 그럼 Aggregator끼리 OnDirty를 구독시키면?

결론: 구독자가 Aggregator일 수 없음.

Agg(공격력)이 "체력 바뀜" 신호를 받아도 할 게 없음. 자기 Mod가 [광전사 +5][무기 +10][저주 -3]인데 어느 게 광전사 건지 모르고 공식도 모름. 재계산할 수 있는 건 공식을 아는 GE뿐.

그래서 GE가 구독해야 하고 — 그게 Dependents. 델리게이트냐 리스트냐 차이만 남음. 리스트가 이기는 이유:

- GE는 수시로 사라짐(만료/제거/디스펠). 델리게이트면 해제 누락 = 죽은 객체 호출. 핸들이면 순회 시 유효성 검증으로 끝.
- 델리게이트는 발화만 됨. 열거/중복제거/배칭/사이클 카운터를 붙일 데가 없음.
- 멀티플레이에선 Aggregator가 복제 안 되고 GE 목록만 복제됨. 데이터면 그래프 재구성 가능, 델리게이트면 불가.

옵저버가 틀린 게 아니라, 제대로 하면 자연히 이 모양으로 수렴함.

## Q3. 왜 Attribute가 아니라 GE를 의존 대상으로? 무관한 Attribute까지 갱신되는 거 아닌가?

결론(1) 무관한 갱신은 실제로 안 일어남. 필터가 두 겹:

```
for (i : Spec.Modifiers)
    if (ModDef.ModifierMagnitude
          .AttemptRecalculateMagnitudeFromDependentAggregatorChange(Spec, OutMag, ChangedAgg))
        AttributesToUpdate.Add(ModDef.Attribute)   // 바뀐 것만
```

각 모디파이어가 "내가 저 ChangedAgg를 캡처했나"를 자체 판정. GE가 어트리뷰트 5개를 건드려도 Hp 의존 모디파이어가 1개면 Aggregator 1개만 갱신. 비용은 Modifiers 순회(1~3개)뿐.

결론(2) GE를 거치는 게 우회가 아니라 필연. Attribute→Attribute 엣지는 "다시 계산하라"를 실행할 주체를 안 가리킴. 추가로 따라오는 것: N:M 정리 단순화, 수명 관리(핸들 무효화), 태그 inhibit 연동, 네트워크 재구성.

Unity 적용 포인트: AttemptRecalculate 자리의 "이 모디파이어가 그 Aggregator를 캡처했나" 판정이 반드시 필요. 없으면 진짜로 무관한 어트리뷰트까지 갱신됨. → Capture 쪽 이미 만들어둬서 금방 추가 가능.

## Q4. B = B * 10 자가 순환이 나나?

결론: 캡처 종류에 따라 갈림.

| | Snapshot | Non-snapshot |
|---|---|---|
| **BaseValue** | 적용 시 base 복사 | base 추적, 자기 참조 안전 |
| **CurrentValue** | 적용 시 최종값 복사 | 최종값 추적, 자기 참조 시 순환 |

- CurrentValue + non-snapshot: 재계산 시 자기 Mod 포함된 값을 읽음 → 매 바퀴 10배 → count 11에서 컷오프. 크래시는 안 나고 값이 쓰레기.
- BaseValue + non-snapshot: BaseValue는 Mod와 별도 저장소, UpdateAggregatorMod가 안 건드림 → 입력 불변 → 2~3바퀴에서 안정.

우하단 칸만 위험. bSnapshot과 별개로 BaseValue/CurrentValue가 두 번째 축이라는 걸 놓치기 쉬움.

Unity 적용 포인트: GAS는 이 실수를 런타임 로그로만 알림. 에셋 검증 시점에 잡을 것 — "모디파이어의 대상 어트리뷰트 == 자신이 non-snapshot CurrentValue로 캡처한 어트리뷰트"면 경고. 조건이 단순해서 구현 비용 거의 없음.

## Q5. 이 복잡한 설계를 그대로 포팅하는 게 맞나? 내부를 좀 더 풀어써도 되나?

전제: 결과물 동작은 유지, 내부 구현만 직관적으로. → 정상적인 포팅.

**풀어써도 되는 것 (언리얼 제약이 원인)**

- 핸들 간접참조 → C#은 GC 있으니 참조 직접 보관 + IsValid 플래그. FFastArraySerializer의 재할당/셔플이 없으므로 핸들 이유의 절반이 소멸.
- 채널 다중화 → 필요할 때 추가
- TArray<FAggregatorMod> Mods[Op::Max] → List<Mod> + Op 필드
- Bias 트릭(Sum += Mod - Bias) → 의도가 드러나게 재작성
- FScopedAggregatorOnDirtyBatch static 전역 → 명시적 컨텍스트 객체
- Spec/Def 분리 → 필요시 통합

**동작이 바뀌는 것 (조심)**

- remove-then-readd → in-place: Mod에 안정적 ID 필요. "GE가 같은 어트리뷰트를 두 번 수정" 케이스 처리 결정 필요.
- 곱셈 스태킹: GAS는 1.5+1.2 → 1.7. 1.8로 바꾸면 밸런스 수치 전부 달라짐.
- 스택 배율이 값에 미리 곱해진 구조 → Evaluate 시점 곱셈으로 옮기면 Override와의 상호작용이 달라짐.
- 사이클 컷오프 10회 → 1회로 줄이면 수렴형 상호의존이 틀린 값으로 굳음.

방법: 동작을 테스트로 고정하고 내부는 자유롭게. 고정할 케이스 —

- 곱연산 두 개 스태킹 결과
- Override 존재 시 다른 Mod 무시 여부
- 스택 3일 때 값
- 순환 의존 시 무한루프 안 나는지
- 캐스케이드 중 GE 제거해도 안 터지는지

없으면 "풀어쓴 게 아니라 미묘하게 다른 걸 만든" 상태를 몇 주 뒤에 발견하게 됨.

## Q6. GAS는 스파게티인가 체계적인가

관찰: 책임과 의존이 일방적이지 않고 유기적. 스파게티 같기도 하고 체계적이기도 함.

결론: 통합적 설계가 아니라 누적된 사후 대응. 파라곤/포트나이트에서 실제로 터진 문제들의 흔적(사이클 카운터 10, 스코프 락, 배칭). 그래서 통합적으로 안 읽히는 게 당연함. 국소적으로 타당한 결정들이 겹쳐서 촘촘해 보이는 것.

## Q7. "가져다 쓰면서 본질을 약간 얻는" 느낌이 드는데, 어느 수준을 목표해야 하나

기준선: "이 결정이 어떤 제약에서 나왔는지 말할 수 있고, 제약이 달라지면 결정이 어떻게 달라지는지도 말할 수 있는 상태."

예 — remove-then-readd를 보고:

- "비효율적이니 in-place로 바꾸고 싶다" → 취향
- "Mod에 ModIdx가 없어서 대응이 안 되니 통짜 교체다. GE당 모디파이어 1개 제약을 걸면 in-place 가능하고, 그 제약을 깨면 무너진다" → 이해

차이는 대신 뭘 포기하는지를 아는가.

이게 시스템 전체에 동시에 성립할 필요는 없음. 통합적 이해 = 모든 걸 동시에 올리는 게 아니라, 필요할 때 그 부분을 이 수준으로 끌어올릴 수 있는 능력.

실질 판단: "언제 도달하냐"보다 "어디까지 이 수준을 확보하고 넘어갈 거냐"를 정하는 게 나음. Attribute/Effect/Aggregator 축을 대표 사례로 굳히고, 나머지는 동작 수준으로 옮긴 뒤 "여긴 원본 구조를 따랐다"고 인정.

자가 테스트: 원본 안 보고 요구사항만으로 30분 스케치 후 GAS와 비교. 다르면 왜 다른지, 같으면 왜 수렴했는지.

## Q8. 제약과 결정, 그리고 기본기

순서 교정: 제약은 "거는" 것이기 전에 "발견하는" 것. GAS의 제약 대부분은 Epic이 고른 게 아니라 주어진 조건(GE는 언제든 사라짐, 배열은 재할당됨, 클라는 GE 목록만 받음).

실제 순서:

1. 주어진 제약을 정확히 읽는다 ← 가장 자주 실패하는 지점
2. 그 아래 가능한 선택지를 본다
3. 필요하면 제약을 추가로 건다 (범위를 좁혀 문제를 쉽게 만듦)
4. 대가를 안다

"기본기"에 대해: 미리 쌓아두고 판단력이 생기는 게 아니라, 판단을 반복하면 기본기로 남는 쪽. 도메인마다 따로 놈 — 지금 얻은 건 "상태 전파 시스템"에 대한 감각이고, 렌더링/네트워크 동기화에선 처음부터 다시 쌓임.

습관: 코드에 결정이 아니라 제약을 주석으로 남길 것.

```csharp
// 전제: 하나의 GE가 같은 Attribute를 두 번 이상 수정하지 않는다.
// 이 전제가 깨지면 in-place 갱신이 무너지고 remove-readd로 돌아가야 함.
```

이게 쌓인 목록이 기본기의 실체 — 추상 능력이 아니라 "어디를 건드리면 뭐가 무너지는지"의 목록.
