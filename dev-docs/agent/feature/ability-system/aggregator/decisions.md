# aggregator — 결정 기록

> 트레이드오프가 있었던 설계 결정의 상세. 품질 기준은 [feature/HARNESS.md](../../HARNESS.md)의 '결정 기록 품질 기준'.
> **ID(`D#`)는 feature 내 고유·불변**이며 progress 인덱스·worklog가 이 코드로 이 표를 가리킨다.
> UE `FAggregator` 원문 확인 근거는 [architecture/ability-system/aggregator.md](../../../../project/architecture/ability-system/aggregator.md) 참조.

> **⚠ 2026-08-09 — D1·D2·D4 폐기(→D5로 대체), D3 재검토.** 유저가 "경량 R3-only" 전제 자체를 뒤집어 **진짜 per-attribute/per-channel Aggregator + 기존 계산 이관**으로 방향을 확정했다. 아래 D1·D2·D4의 채택 사유는 폐기된 전제 위에 서 있으므로 **이력으로 보존하되 현재 방향이 아니다.** 경위·잘못은 [worklog 2026-08-09](worklog.md).

| D1 | 2026-08-07 | 라이브 재평가를 위해 **UE aggregator의 반응성 책임(R3: 의존+dirty+재평가)만 별도 컴포넌트로 분리**한다. | D4 | 2026-08-08 | 재평가는 **registry 없이**: 변경된 `handle`을 non-snapshot으로 **이 ASC에서** 읽는 persistent 스펙만 활성 목록에서 스캔·필터해 재평가한다. 연쇄는 **worklist + visited(handle)**로 유한 전파(자기참조/순환은 재방문 차단으로 1패스 종료). 반응성 로직은 `AttributeAggregator`(ASC 소유·`AttributeChanged` 구독)가 갖고, ASC는 `ReevaluateDependents(handle)`·Spec은 `ReevaluateMagnitudes()`/`DependsOnNonSnapshot(asc,handle)` 최소 훅만 노출. **재캡처 없음** — 캡처가 이미 조회 시점 라이브(`GameplayEffectAttributeCaptureSpec.TryGetCapturedValue`). | ① 전량 재평가 + bool 가드(1홉만, 연쇄 미전파) ② 영속 의존 레지스트리(등록/해지) + dirty 그래프 | 유저 확정: "의존 필터 + worklist". ①은 최소지만 handle 무관 전량 재계산이라 낭비 + 다홉 연쇄 미전파. ②는 정석이나 등록/해지 배선·수명관리 비용이 이 규모(D2 경량)에 과함. 필터+worklist는 레지스트리 없이도 **바뀐 값에 실제 의존하는 것만** 정확히 재평가하고, visited로 유한·자기참조 안전을 함께 얻어 UE dependents 모델에 가장 가깝다. **미커버(수용):** cross-actor(cross-ASC 구독 — `_capturedAsc==owner` 필터로 self-scope 한정)·자기참조 진짜 fixed-point 수렴(1패스만). |
| D5 | 2026-08-09 | **D1 반전(유저 확정).** 반응성만 분리하는 경량안을 폐기하고, UE `FAggregator`에 준하는 **어트리뷰트별·채널별 Aggregator**를 신설해 기존 ASC 인라인 계산(채널 집계 `CalculateAttributeCurrentValue`·base 연산 `ExecuteModOnBaseValue`·평가/dirty)을 그 Aggregator로 이관한다. mod 저장은 이펙트 온디맨드 스캔 → **aggregator 소유**(Apply 등록/Remove 해제)로 바꾸고, per-attribute aggregator 맵을 들 **컨테이너를 신설**한다. | ① 현행(경량 R3-only, D1) 유지 ② 반응성만 계속 분리하고 계산은 ASC 유지 | **유저 확정:** aggregator는 ASC가 하나만 드는 게 아니라 **어트리뷰트별·채널별**로 존재해야 하고, "새로 만든다"면 기존 Attribute 계산이 그 aggregator로 이관돼야 한다. D1의 "full aggregator = 과설계"는 유저 의도가 아니라 에이전트가 목표 확인 전에 내린 단정이었음(HARNESS '해석 규율'). **미확정(유저 결정 대기): BaseValue 소유 주체 — Aggregator vs AttributeData.** 데이터 모델을 가르는 지점이라 이 결정 확정 후 세부 범위·순서를 정한다. **트레이드오프:** UE 정합·구조 명확(계산 책임이 aggregator로 응집)을 얻는 대신, Apply/Remove/Execute 경로의 광범위 변경 비용과 컨테이너 레이어 신설 비용을 감수. **재평가 트리거:** 이관 규모가 과도해 데모 진행을 저해하면 범위를 어트리뷰트 일부로 좁힌다. |

| D3 | 2026-08-08 | 어트리뷰트 변경 이벤트는 **`UpdateAttributeCurrentValue` 단일 choke point**에서 발화한다(`(handle, old, new)`, 값이 실제로 바뀔 때만). 핸들러는 Base/Current 어느 캡처든 **라이브 재조회**로 재평가한다. | ① progress 원안: `SetBaseAttributeValue`+`UpdateAttributeCurrentValue` 2곳 ② Base·Current 별도 두 채널(모든 Base 쓰기 지점 포함) | 코드 확인 결과 ASC의 어트리뷰트 쓰기 지점은 셋(`SetBaseAttributeValue`·`ApplyEvaluatedModifier`[Execute 경로 Base]·`UpdateAttributeCurrentValue`[Current])인데, **Base 쓰기 1·2가 전부 `RecalculateAttributeCurrentValue → UpdateAttributeCurrentValue`로 수렴**한다. 그래서 3번 한 곳이 "값이 유효하게 바뀜"의 단일 choke point가 된다 — progress 원안(①)은 Execute 경로 Base 변경(GE가 힘을 바꾸는 수용 기준 핵심 시나리오)을 놓쳐 부적합. 별도 두 채널(②)은 캡처 값종류에 정밀 대응하나 배선이 늘고 과발화 여지가 있어, 지금 규모(D2 경량)에선 단일 채널+핸들러 라이브 재조회로 충분. **미커버(수용): Base만 바뀌고 Current는 그대로인 희귀 경우(Override 고정 등)** — 실제 수요 시 ②로 승격. |
| D7 | 2026-08-10 | **⚠ 2026-08-16 D14로 반전(base 진실 → AttributeData). 아래는 이력으로 보존.** **D5 선결 미확정 해소(유저 확정) — BaseValue 소유 주체 = Aggregator.** per-attribute `AttributeAggregator`가 BaseValue를 필드로 소유한다. base 변경은 `SetBaseValue()`로, current는 `Evaluate()`로만 취득한다(외부는 Evaluate 외 계산 경로 없음 — 유저 지시). `AttributeData.BaseValue`는 저장/동기화 미러로 남고, aggregator 지연 생성 시 그 값으로 시드한다. | ① AttributeData가 BaseValue 진실 + Aggregator는 base를 인자로 받아 집계만(`Evaluate(base)`) ② Aggregator 소유 + AttributeData 미러 | **유저 확정(UE 근접):** UE `FAggregator`가 BaseValue를 보유(참고문서 §11: AttributeData.BaseValue → Aggregator.BaseValue → Evaluate → CurrentValue)하므로 계산 기준값이 aggregator에 응집돼야 "외부는 Evaluate로만"이 성립한다. ①은 저장 이원화를 피하지만 aggregator가 base를 안 들어 UE 소유관계와 갈리고 매 평가에 base를 밖에서 주입해야 함. **트레이드오프:** base 저장이 이원화(aggregator=진실, AttributeData=미러)돼 **동기화 규율**(base 쓰는 모든 경로가 둘 다 갱신)을 사람이 지켜야 함. **재평가 트리거:** 미러 동기화가 버그원이 되면 AttributeData 단일 진실로 회귀. |
| D12 | 2026-08-11 | **cross-attr 라이브 재평가 복원 방식 = UE 원문식(유저 확정, 미구현).** 어트리뷰트 간 라이브 재평가(A 변경→A에 non-snapshot 의존하는 이펙트 magnitude 재평가)를 **UE의 의존 등록 + `OnDirtyRecursive` cascade + `MAX_BROADCAST_DIRTY` cap** 방식으로 복원한다. 구조: 소스 aggregator가 `Dependents`(의존 이펙트 핸들)를 들고, dirty 시 `OnMagnitudeDependencyChange`로 의존 이펙트의 mod magnitude를 소스 새 current로 재계산→대상 aggregator 재동기화→재broadcast. 순환은 cap으로 차단(해결 아님). | ① 위상정렬(topological) 재평가 — 의존 그래프를 Base부터 위상순서 1회씩 계산, 순환은 정렬 실패로 감지·거부 ② 옛 전량 스캔 방식 | **유저 확정: "ue 기준으로", "ue를 따른다".** 에이전트가 대안 ①(위상정렬 — DAG면 중복 재계산 없고 순환을 감지로 처리, 더 깔끔)을 제시했으나 유저가 UE 정합을 택함. **핵심 이해(재평가):** `Evaluate`는 늘 Base+mod로 재계산하는 순수 함수라, 재평가 = 의존 mod magnitude를 소스 새 값으로 갱신 후 대상 Evaluate 재실행.
