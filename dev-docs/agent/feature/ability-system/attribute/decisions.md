# attribute — 결정 기록

> 트레이드오프가 있었던 설계 결정의 상세. 품질 기준은 [feature/HARNESS.md](../../HARNESS.md)의 '결정 기록 품질 기준'.
> **ID(`D#`)는 feature 내 고유·불변**이며 progress 인덱스·worklog가 이 코드로 이 표를 가리킨다.
> 이 시스템은 **UE GAS를 참고해 필요한 축만 직접 구현**한 것 — 각 행의 `(UE 대응)` 표기와 전체 채택/생략 범위는 [architecture overview](../../../../project/architecture/ability-system/overview.md) 참조.

| ID | 날짜 | 결정 | 대안 | 채택 사유 |
|---|---|---|---|---|
| D1 | 2026-05-26 | `AttributeHandle`을 **불변 struct로 두고 생성 시 `FieldInfo`를 캐싱**. `SetType + fieldName` 기반 `IEquatable`로 Dictionary 키 사용 | ① string 키 Dictionary(매 접근 문자열 조회) ② enum 키 + switch | 수치 읽기는 매 프레임 다수 발생 → 접근 경로에 string 탐색이 있으면 비용이 누적된다. Reflection을 **생성 1회로 격리**하면 이후 읽기/쓰기는 캐싱된 FieldInfo로 O(1). struct라 GC 부담도 없음. 트레이드오프: 핸들 선언이 `static readonly` 보일러플레이트를 요구하나, 접근 성능과 타입 안전(INV: untyped 저장 금지 정신)이 우선. **(UE 대응)** UE `FGameplayAttribute`는 `UProperty`로 필드를 가리키지만 Unity엔 그 기반이 없어, `FieldInfo`를 생성 1회 캐싱하는 struct로 같은 목적을 축소 재현 (→ 2026-08-21 D5에서 `ResolvedGameplayAttribute`로 리네임하고 UE 대응을 "런타임 해석·접근 절반"으로 재해석) |
| D2 | 2026-05-26 | `AttributeSet`은 **빈 추상 마커**, 구체 Set(`Character`/`Combat`)이 `public AttributeData` 필드로 수치를 보유. ASC는 `Dictionary<Type, AttributeSet>`로 타입당 하나 등록 | 모든 수치를 한 Set/Dictionary<string,float>에 몰아넣기 | 수치를 도메인(캐릭터 vs 전투)별 Set으로 나누면 필요한 Set만 붙일 수 있고(적/상자엔 Combat만 등 재사용), 필드가 컴파일타임에 존재해 오타·타입 오류를 막는다. untyped 블랙보드(문자열 키) 회피. **(UE 대응)** UE `UAttributeSet`(수치를 클래스 컨테이너로) 개념 채택 |
| D3 | 2026-05-26 | 초기값은 **`AttributeInitData`(SO) → Reflection(`Activator.CreateInstance`+`FieldInfo.SetValue`)**으로 세팅. 에디터 드로어가 Set·필드·값을 배선 | 코드/인스펙터에 초기값 하드코딩 | 밸런싱 값을 코드 수정 없이 데이터로 조정 가능해야 함. SO로 빼면 디자이너가 에디터에서 만지고, 같은 ASC 초기화 코드가 임의 Set에 일반화된다. 트레이드오프: 초기화에 Reflection 1회 비용이 있으나 Awake 시점 1회라 무시 가능. **(UE 대응)** UE는 GE·CurveTable로 초기값을 주지만, 여기선 전용 SO+Reflection으로 축소 |
| D4 | 2026-08-07 | 타입 선택 UI에서 **"New Script..."** — 이름을 적으면 baseType(여기선 `AttributeSet`)을 상속한 빈 서브클래스 .cs를 템플릿으로 생성하고, **컴파일·도메인 리로드 후 그 타입을 자동 배정**. 진입점 둘: **다형 리스트 add "+"**(새 요소로 추가) + **SubclassSelector 필드 "+"**(기존 요소 타입 변경). 리로드로 팝업·SerializedProperty가 무효화되므로, 재배정 정보는 `SessionState`에·대상은 리로드를 넘겨도 유효한 `GlobalObjectId`로 식별해 `[DidReloadScripts]`에서 배정(Field=필드에 AQN 세팅 / Add=배열에 요소 삽입 후 세팅). New Script는 **호출부별 opt-in**(리스트는 `newScriptBaseType`, 필드는 `allowCreateNew`)이라 AttributeSet에만 노출. 겸사겸사 리스트 add 팝업을 `GenericMenu`→**검색형 `AdvancedDropdown`**으로 통일(필드 셀렉터와 동일 UX, Item 모듈 리스트도 검색 가능해짐) | ① 파일만 생성하고 사용자가 컴파일 후 재선택 ② 생성 UI를 OS 저장 다이얼로그(`SaveFilePanelInProject`)로 ③ New Script를 필드 셀렉터에만 | 새 Set을 만들 때 스크립트 생성→골격 작성→다시 열어 선택의 왕복을 한 번으로(UE Blueprint "New Class"류). 유저는 새 Set을 **리스트 "+"에서** 만들려 하므로 그 진입점이 1순위 → 거기에 넣고 필드 셀렉터에도 유지. 리로드 넘김이 난점 → 직렬화 참조 대신 `GlobalObjectId`+`SessionState`. 생성 UI는 Add Component→New Script처럼 **인라인 이름 입력**(OS 다이얼로그 아님), 타입 목록도 Add Component처럼 **검색 가능**. **(UE 대응 없음 — 에디터 편의 툴)**. 공용 코드 `Core/Common/Editor`(`SubclassAdvancedDropdown`·`SubclassSelectorDrawer`·`TypeChoiceList`·`NewSubclassScriptPopup`) |
| D6 | 2026-08-22 | `AttributeSet`에 **소유 ASC back-reference(`owner`) 추가**. 어트리뷰트별 쓰기 편의 접근자(`AttributeSet.SetBaseValue(handle, value)`)를 이 owner를 통해 ASC(`SetAttributeBaseValue`)로 위임. **⚠ 주입 방식 미확정·미완(2026-08-22):** `SetOwner`(등록 시점 주입)로 시작했다가 유저가 **생성자 주입**으로 전환 — 현재 `AttributeSet`에 생성자만 있고 서브클래스 전달 생성자·`Activator.CreateInstance` 인자가 미배선이라 **컴파일 불가**. 다음 세션에 방식 확정 후 배선 완성 필요 | ① `AttributeSet.SetAttribute(handle, value)` generic 세터(back-ref 없이) ② ASC 경유만 강제(편의 접근자 없음) ③ 타입별 이름(`SetHealth`)을 Roslyn Source Generator로 일괄 생성 | UE `ATTRIBUTE_ACCESSORS`의 `SetX`도 실제로는 `GetOwningAbilitySystemComponent()->SetNumericAttributeBase(...)`로 **ASC에 위임**한다(웹 다수 출처 확인) — 즉 "Set에 두기 vs ASC로만"은 양자택일이 아니라 *얼굴은 Set, 쓰기는 ASC 위임*이며, 그러려면 Set이 owner를 알아야 한다. generic 세터(①)는 호출부가 못생기고, ASC-only(②)는 어트리뷰트 식별을 매번 호출부가 들고 다녀야 함. 타입별 이름 자동생성(③)은 C#에 전처리 매크로가 없어 Source Generator가 유일 등가물이나 제너레이터 유지비가 있어 **보류** — 지금은 owner를 통한 핸들 기반 접근자로 "일괄 적용"만 확보. 트레이드오프: Set→ASC 순환 참조가 생기나 소유 관계상 자연스럽고 주입을 등록 1지점으로 제한해 수명 일관. **(UE 대응)** `UAttributeSet::GetOwningAbilitySystemComponent` + `ATTRIBUTE_ACCESSORS`의 SETTER 위임 절반. *재평가 트리거: 값 접근자 타입별 이름(`SetHealth`)이 필요해지면 ③(Source Generator) 재검토* |
| D5 | 2026-08-21 | `AttributeHandle` → **`ResolvedGameplayAttribute`** 리네임 + UE 대비 개념 정리. UE는 단일 `FGameplayAttribute`(직렬화 FName + 해석된 `FProperty` + 값 접근자)인데, 이 프로젝트는 이를 **직렬화용 `GameplayAttribute`**(문자열 쌍 AQN+필드명, 전용 드로어)와 **런타임 해석·접근용 `ResolvedGameplayAttribute`**(FieldInfo 캐싱, `TryGet/SetData`) 둘로 나눠 둔 것임을 명확화. 변환 메서드도 `ToAttributeHandle()`→`ToResolvedAttribute()`. D1을 이 이름·해석으로 갱신 | ① `AttributeHandle` 이름 유지 ② 한 타입으로 병합(UE처럼 `ISerializationCallbackReceiver`로 문자열→FieldInfo 지연 해석·캐싱) ③ 런타임 타입에 `GameplayAttribute` 이름을 주고 직렬화 타입을 개명 | 분리의 근본 원인은 **C#이 `FieldInfo`를 직렬화하지 못함**(UE는 `UProperty`/FName으로 한 타입에 담음). "Handle"은 불투명 조회 토큰 뉘앙스라, `SetType`/`Name`을 노출하고 값까지 접근하는 이 타입엔 부정확 — 게다가 코드베이스에서 `ActiveGameplayEffectHandle`이 이미 "불투명 런타임 ID"로 그 단어를 점유해 의미가 겹친다(①거부). 두 타입의 실제 차이 축은 **해석 여부**라 `Resolved-`가 그 축을 이름으로 설명한다. `GameplayAttribute`(직렬화) 이름은 UE에서 직렬화 필드 타입이 `FGameplayAttribute`인 자리와 맞아 유지(③거부). 병합(②)은 struct 지연 캐싱(값 복사 이슈)·동등성 기준 통합이 필요한 실질 리팩터라 지금은 보류하고 현 2타입 구조를 유지. **(UE 대응)** 두 타입의 합이 UE `FGameplayAttribute` — 직렬화 절반=`GameplayAttribute`, 런타임 절반=`ResolvedGameplayAttribute` |
