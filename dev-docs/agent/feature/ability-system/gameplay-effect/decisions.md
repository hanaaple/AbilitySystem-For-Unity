| D9 | 2026-07-19 | **Execute 경로의 어트리뷰트 쓰기 지점을 `ApplyEvaluatedModifier` 하나로 통합한다.** Modifier와 Execution 출력이 같은 함수를 통과하며, 연산 적용은 `ExecuteModOnBaseValue`가 담당 | Modifier 루프와 Execution 출력 루프가 각자 switch를 갖는 현행 유지 | 통합 전에는 **같은 "어트리뷰트에 연산 적용"인데 경로에 따라 능력이 달랐다** — Modifier는 6종 전부, Execution 출력은 `AddBase`/`Override` 2종만(나머지는 경고 후 무시). 이건 의도한 축약이 아니라 로직 중복에서 온 결함이고, 경로가 둘인 한 계속 어긋난다. | D10 | 2026-07-19 | **BaseValue를 쓸 때마다 그 자리에서 CurrentValue를 재계산한다** (modifier 1건·Execution 출력 1건 단위) | 한 GE의 Modifier·Execution을 모두 처리한 뒤 영향받은 어트리뷰트를 **마지막에 일괄** 재계산 (기존 구현) | 일괄 방식은 **뒤따르는 Modifier·Execution이 stale CurrentValue를 읽는 버그**를 만들었다 — 같은 GE의 modifier가 BaseValue를 바꿔도 CurrentValue는 갱신 전이라, `RunExecutions`의 Execution이 `GetAttributeCurrentValue`로 옛 값을 읽었다. 이는 D3가 트레이드오프로 적어둔 "재계산 트리거를 빠뜨리면 stale" 위험이 실제로 터진 사례다. | D11 | 2026-07-19 | **Execution의 입력/출력을 두 타입으로 분리하고, 둘 다 struct로 두며, execution 스코프 지역 변수로 만든다.** `GameplayEffectExecutionParameters`(입력) + `GameplayEffectExecutionOutput`(출력) + `GameplayModifierEvaluatedData`(결과 1건) | ①입력 객체가 출력 목록까지 들고 있던 기존 구조 ②분리하되 둘 다 class ③분리하되 인스턴스를 재사용(`Clear()`)해 할당 회피 | **분리 이유:** 기존엔 `ExecutionParameters`가 `AddOutput`/`Outputs`까지 갖고 있어 "입력"과 "출력 수집기" 두 역할이 섞였다.
