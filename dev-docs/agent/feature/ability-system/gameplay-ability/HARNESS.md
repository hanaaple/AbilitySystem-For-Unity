# gameplay-ability/HARNESS — GA 작업 방향·프로세스

이 feature(GA)의 **작업 프로세스·에이전트 규율**을 고정한다(규칙=어떻게).
요구사항·범위·목표(무엇을)는 → [requirements.md](requirements.md).

---

## 작업 프로세스 (방향성, 고정 절차 아님)

> **확정된 체크리스트가 아니다.** 유저 명시: 그때그때 바뀌고 빠질 수 있으며 **중요한 건 방향성**이다. 순서를 경직되게 강요하지 않는다.

1. **이해가 구현에 선행한다.** 유저가 GA를 이해하는 것이 우선. 수단: **AI 분석 + 유저의 소스코드 직접 확인 + 리서치** 혼용.
2. **이해 → 유저 의도에 따라 이식·구현 방식을 정한다.** 구현 주체는 **유저 또는 AI**.
3. **이해와 구현의 순서는 유동적이다.** 완전 이해 후 구현 / 부분 이해 후 구현 / 반복 / 혼용 — 정해두지 않는다.
4. **완성 후 테스트한다 — 유저 직접 + AI로도.**

---

## 에이전트 운영 규율 (이 feature 고유 — 상위 규약은 참조만)

1. **이해 단계에선 구현으로 튀지 않는다.** 유저가 이해 중이면 분석·설명·근거에 집중하고, 구현은 **유저 신호가 있을 때** 착수한다.
2. **범위(무엇을 넣고 뺄지)는 유저가 판단한다.** 내가 임의로 확정하지 않고, 필요하면 **선택지·트레이드오프 제시까지만** 한다(결론 못박지 않음). ※ UE 원본 동작은 원문 확인 후 짚는다(→ agent/HARNESS 원칙5).
3. **유저가 순서를 바꾸면 따라간다.**
4. **문서의 근거 태그** — requirements 등은 `[유저]`·`[progress]`·`[코드]`로 근거를 구분한다(근거 명시·문서 분리 규약은 → agent/HARNESS 원칙5·8·9).
