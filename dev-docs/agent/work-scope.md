# work-scope — 작업 착수·범위 규약

**유저 요청을 받아 무엇을 얼마나 할지 정할 때 따른다** — 코드·문서·에셋을 만들거나 고치기 전. 상위: [HARNESS.md](HARNESS.md).

---

## 착수 — 명시적 지시가 있을 때만

- **설계 논의 중에는 구현에 착수하지 않는다 — 제안까지만.** 방향이 그럴듯해 보여도 동의로 판단하지 않고, 구조 스케치·트레이드오프까지 내놓고 "이 방향으로 구현할까?"에서 멈춘다. `구현해줘`·`해봐`·`가자` 같은 **명시적 착수 지시**가 있을 때만 파일을 만든다.
- **순서 합의 ≠ 착수 지시.** "다음엔 X 하자"는 무엇을 할지의 합의지 지금 쓰라는 게 아니다.
  - **"X 하자. 그 전에 Y 하고" = Y만 하고 멈춘다.** 이번 턴 지시는 Y 하나. NOW.md·progress에 X가 "다음 액션"이어도 그건 로드맵이지 이번 턴 착수 지시가 아니다.

- **총량을 바꾸지 않는 확인은 묻지 않는다 — 단 지금 지시받은 작업 안에서만.** 유저 2026-10-21: "총량을 없애거나 바꾸는게 아니면 하라고"(TODO 정리 중 "이 순서로 갈까요?"에 대한 답). 지시받은 작업(그때는 TODO 정리)의 순서·구성처럼 **총량을 빼거나 바꾸지 않는 것**은 확인을 구하지 않고 정해서 기록한다. **이건 다른 작업(구현 등)의 착수 지시가 아니다** — 2026-10-21 에이전트가 이 말을 구현 착수로 읽어 데모 0~4를 구현했다가 유저 "아니 왜 구현하고 있어 TODO만 하라니까".

## 범위 — 지시된 것만

- **착수 지시를 받았어도 범위는 지시된 것만.** 없는 것(필드·API·에셋) 발견 = 멈추고 물을 지점. **데이터 모델·기존 동작 변경은 항상 별도 승인.**
- 발견한 버그·개선점은 고치지 말고 보고만 한다. 단순 버그도 고치지 않고, 발견한 그 자리에서 바로 얘기한다(유저 2026-10-20: "발견 시 보고만 하는거야. 다만, 단순 버그는 거기서 얘기를 해줘").
- feature 범위가 커지면 임의로 확장하지 않고, 분리 제안을 유저에게 보고한다.
- 코드 설계 쪽 갈림(좁은 스코프·공통화 크기·구조적 개념 도입) → [code-guide/HARNESS.md](code-guide/HARNESS.md) '설계 원칙'.

## 큰 작업은 먼저 묻는다

- **토큰이 크게 나갈 작업은 착수 전에 규모·방식을 먼저 묻는다.** 광범위 참조 추적, 정합성 검증, 다수 파일 일괄 편집, 대규모 리팩터 등은 예상 비용을 알리고 **범위 축소·검증 위임 옵션**을 제시한 뒤 진행한다.
